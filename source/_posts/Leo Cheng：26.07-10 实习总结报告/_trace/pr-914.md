## 问题与原因

Go 程序在 StarryOS 上网络轮询失败，运行时报 `netpoll failed` 与 `fd N failed with 14`（`EFAULT`）。Go 运行时的 `epollevent` 把 `data` 声明为 `[8]byte`，整个结构只按 4 字节对齐，传给 `epoll_ctl` 的地址可能是 8 的倍数加 4。StarryOS 用类型化指针 `*const epoll_event` 读用户内存，辅助函数对未按 8 字节自然对齐的指针直接返回 `EFAULT`。Linux 用 `copy_from_user` 按字节拷贝，没有对齐要求。

x86_64 的 `struct epoll_event` 在 Linux 头文件里是紧凑布局（12 字节，对齐 1），问题主要出现在 aarch64、riscv64、loongarch64 这些 16 字节、8 字节对齐的架构上。

## 改动与影响范围

| 修改点 | 内容 |
|:--:|:--:|
| `read_epoll_event()` | 新增，经 `vm_read_slice` 按字节读入 `epoll_event` |
| `write_epoll_event()` | 新增，经 `vm_write_slice` 按字节写出 |
| `sys_epoll_ctl` | 读取事件改用 `read_epoll_event` |
| `do_epoll_wait` | 回写就绪事件改用 `write_epoll_event` |

影响范围：`epoll_ctl`、`epoll_wait`、`epoll_pwait`、`epoll_pwait2` 的用户缓冲区拷贝。`epoll_event` 是纯数据结构，任意字节组合都合法，按字节拷贝是对齐读写的超集，对齐的调用者行为不变。

当前 dev 仍保留这两个函数（`syscall/io_mpx/epoll.rs` 第 60、84 行）。

### `epoll_ctl` 读事件

合入前（`os/StarryOS/kernel/src/syscall/io_mpx/epoll.rs` 的 `sys_epoll_ctl`，按 `epoll_event` 类型取引用）：

```rust
let parse_event = || -> AxResult<(EpollEvent, EpollFlags)> {
    let event = event.get_as_ref()?;
    let events = IoEvents::from_bits_truncate(event.events);
```

Linux（[fs/eventpoll.c#L2390-L2392](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/fs/eventpoll.c#L2390-L2392)）：

```c
	if (ep_op_has_event(op) &&
	    copy_from_user(&epds, event, sizeof(struct epoll_event)))
		return -EFAULT;
```

本 PR（同一文件；当前 dev 上 `read_epoll_event` 与 `write_epoll_event` 都在，各多一个 `current` 参数）：

```rust
fn read_epoll_event(event: UserConstPtr<epoll_event>) -> AxResult<epoll_event> {
    let mut buf = MaybeUninit::<epoll_event>::uninit();
    let dst = unsafe {
        core::slice::from_raw_parts_mut(
            buf.as_mut_ptr().cast::<MaybeUninit<u8>>(),
            size_of::<epoll_event>(),
        )
    };
    vm_read_slice(event.address().as_ptr(), dst)?;
    // SAFETY: all bytes were just initialized by the copy above and any bit
    // pattern is a valid `epoll_event` (plain old data).
    Ok(unsafe { buf.assume_init() })
}
// ...
let parse_event = || -> AxResult<(EpollEvent, EpollFlags)> {
    let event = read_epoll_event(event)?;
```

### `epoll_wait` 回写

合入前（同一文件的 `do_epoll_wait`，按 `epoll_event` 类型的指针写回）：

```rust
epoll.poll_events_with(maxevents, |index, event| {
    vm_write_slice(
        events.as_ptr().wrapping_add(index),
        core::slice::from_ref(&event),
    )?;
    Ok(())
})
```

Linux（[include/linux/eventpoll.h#L85-L92](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/include/linux/eventpoll.h#L85-L92)）：

```c
static inline struct epoll_event __user *
epoll_put_uevent(__poll_t revents, __u64 data,
		 struct epoll_event __user *uevent)
{
	scoped_user_write_access_size(uevent, sizeof(*uevent), efault) {
		unsafe_put_user(revents, &uevent->events, efault);
		unsafe_put_user(data, &uevent->data, efault);
	}
```

本 PR（同一文件，目标指针转成 `*mut u8` 后再写）：

```rust
fn write_epoll_event(
    events: UserPtr<epoll_event>,
    index: usize,
    event: &epoll_event,
) -> AxResult<()> {
    let dst = events.as_ptr().wrapping_add(index) as *mut u8;
    let src = unsafe {
        core::slice::from_raw_parts(
            event as *const epoll_event as *const u8,
            size_of::<epoll_event>(),
        )
    };
    vm_write_slice(dst, src)?;
    Ok(())
}
// ...
epoll.poll_events_with(maxevents, |index, event| {
    write_epoll_event(events, index, &event)?;
    Ok(())
})
```

## man 原文

[epoll_wait(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/epoll_wait.2?h=man-pages-6.19#n192)：

> EFAULT The memory area pointed to by events is not accessible with write permissions.

man 只把 `EFAULT` 限定为「不可写」，没有对齐要求，未对齐但可写的缓冲区不应得到 `EFAULT`。

## 验证

- 当时：`cargo xtask starry build --arch x86_64` 通过；既有 `test-epoll`、`test-epoll-eventfd`、`test-epoll-lt`、`test-epoll-pwait2` 回归不变。
- 缺口：拉取请求没有带一个构造「8 的倍数加 4」地址的确定性用例，没有在修复前验证红。
- 后续：6 月 4 日 prometheus 在 riscv64、loongarch64 上报同样的 `EFAULT`，`notes/71` 插桩定位到 `starry-vm` 中 `vm_write_slice` 的 `is_aligned()` 检查。本拉取请求的两个辅助函数以 `*u8` 指针调用它（对齐要求为 1），不会触发这道检查；note 71 排查的分支里 `do_epoll_wait` 仍按 `epoll_event` 类型写回（记录中的 `epoll.rs:124`），说明那条分支没有包含本修复。[#921](pr-921.md) 随后在底层删除了对齐检查，所有调用点都不再依赖对齐。
