## 问题与原因

`FileBackend::populate` 对传入范围内的每一页都取页缓存页并建立映射，不看这一页的文件偏移是否已经越过文件长度。映射比文件大得多时，物理内存的占用跟着映射大小走，而不是跟着文件大小走。

PR 正文给的触发场景是 etcd 内嵌的 bbolt：以约 10 GiB 的 `InitialMmapSize` 映射一个十几 KiB 的数据库文件，内核为某次系统调用预取这段用户缓冲区时（`mm/access.rs` 的 `check_region` 到 `populate_area` 再到 `FileBackend::populate`），一次调用覆盖整个映射，逐页分配，到约 40 万页时内存耗尽。正文记录的实测值是 `range_pages=2621440 / eof_page=4`。带 `MAP_POPULATE` 的大映射走的是同一个函数。

第二处问题在评审中提出：`CachedFile::page_or_insert` 读入磁盘页时不处理短读。按补丁注释，`PageCache::new()` 不清零新分配的帧，`FileNodeOps::read_at` 在 EOF 处只返回实际读到的字节数、不动缓冲区的其余部分，文件最后一页在 EOF 之后的部分因此保留帧里原有的内容，经映射可被用户态读到。

## 改动与影响范围

| 修改点 | 位置 | 内容 |
|:--:|:--:|:--:|
| `CachedFile::file_len()` | `axfs-ng/src/highlevel/file.rs` | 新增，返回后端文件当前的字节长度（`self.inner.len()`） |
| `FileBackend::populate` | `kernel/src/mm/aspace/backend/file.rs` | 循环前计算 `eof_page = file_len().unwrap_or(u64::MAX).div_ceil(PAGE_SIZE_4K)`；循环内对 `pn >= eof_page` 的页直接 `continue`，不分配也不映射。`div_ceil` 保留最后一个不满的页 |
| `CachedFile::page_or_insert` | `axfs-ng/src/highlevel/file.rs` | 磁盘页读入后，`read < PAGE_SIZE` 时把 `page.data()[read..]` 清零 |

影响范围：经 `FileBackend` 的文件映射在缺页、`MAP_POPULATE`、`mlock` 以及内核预取用户缓冲区时的行为，EOF 之外的页不再有帧；访问这些页时 `populate` 返回 0 页，缺页按未处理上报。`page_or_insert` 的改动作用于所有非内存文件的页缓存读入，`read`、`mmap` 看到的最后一页尾部都是 0。完全位于 EOF 之内的映射不受影响。

与 Linux 的差异（合入时）：

- 越过 EOF 的访问得到 `SIGSEGV`，Linux 是 `SIGBUS`。补丁注释与回归用例都写明了这一点，用例只记录信号编号，不作断言。
- `file_len()` 失败时回退为 `u64::MAX`，即不设上界，退回修复前的行为；Linux 没有对应的回退。

当前 dev：

- `populate` 的上界仍在 `mm/aspace/backend/file.rs` 第 1087 至 1094 行，`file_len()` 的错误改为用 `?` 向上传播，不再回退。单页缺页路径在同文件第 997 至 1000 行有同样的判断。
- `file_len()` 移到 `fs/ax-fs-ng/src/file/cache/mod.rs` 第 650 行；短读清零在同文件第 868 至 869 行，去掉了 `read < PAGE_SIZE` 的判断，直接 `page.data()[read..].fill(0)`。
- 文件映射缺页得到 0 页时返回 `FaultResult::Sigbus(BusCode::AdrErr)`（`mm/aspace/mod.rs` 第 6274 至 6276 行），`task/user.rs` 第 51 行把它转成 `SIGBUS`，上面第一条差异已消除。

## 溯源复核

- PR 正文没有随评审更新。正文写「populate 返回 0 页，缺页处理返回未处理，投递 `SIGBUS`，与 Linux 一致」，合入时实际投递的是 `SIGSEGV`，作者在 2026-06-10 的评论里更正，并把补丁注释改成了现在的写法。正文也没有列出 `page_or_insert` 的短读清零和回归用例，二者都是评审后加入的。
- 正文说修复前 EOF 之外的页分到的是「零页帧」。按补丁自己的注释，新分配的帧并不清零，短读也不填充缓冲区，所以修复前这些页与最后一页的尾部带着帧里的旧内容映射给用户态。两处改动合起来消除的不只是内存占用，还有这条内容泄露的路径。
- `page_or_insert` 的短读清零就是 [#1114](pr-1114.md) 标题里宣布、后来从那个 PR 移出的 axfs-ng 尾页清零。
- 评审机器人多次写到「Linux 下 `MAP_PRIVATE` 映射越过 EOF 应得到零填充页」，并把它列为后续改进。这一说法与 Linux 不符：私有映射的读缺页与写时复制缺页都先调用映射的 `fault` 回调，`filemap_fault()` 在入口处对 `index >= max_idx` 一律返回 `VM_FAULT_SIGBUS`，不区分共享与私有；man 对 `SIGBUS` 的描述也没有这个区分。补丁对两类映射一视同仁是对的。
- 回归用例已不在当前 dev 的树里，见「验证」。

## man 原文

[mmap(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/mmap.2?h=man-pages-6.19#n640)：

> SIGBUS Attempted access to a page of the buffer that lies beyond the end of the mapped file. For an explanation of the treatment of the bytes in the page that corresponds to the end of a mapped file that is not a multiple of the page size, see NOTES.

[mmap(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/mmap.2?h=man-pages-6.19#n769)：

> A file is mapped in multiples of the page size. For a file that is not a multiple of the page size, the remaining bytes in the partial page at the end of the mapping are zeroed when mapped, and modifications to that region are not written out to the file.

[mmap(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/mmap.2?h=man-pages-6.19#n376)：

> MAP_POPULATE (since Linux 2.5.46) Populate (prefault) page tables for a mapping. For a file mapping, this causes read-ahead on the file. This will help to reduce blocking on page faults later. The mmap() call doesn't fail if the mapping cannot be populated (for example, due to limitations on the number of mapped huge pages when using MAP_HUGETLB).

## 验证

- `syscall-test-mmap-populate-eof`（7 条断言）：建一个 100 字节的文件，以 256 MiB 的 `MAP_SHARED | MAP_POPULATE` 只读映射。用例所在的组以 512 MiB 内存运行，映射成功本身说明没有按映射大小分配。随后断言 `[0, 100)` 是文件内容 `0xAB`；`[100, 4096)` 全为 0；读偏移 4096 处触发信号；读映射末页触发信号。信号的编号只打印，不断言是 `SIGBUS` 还是 `SIGSEGV`。
- 作者 2026-06-10 的评论：x86_64、aarch64、riscv64、loongarch64 单核 QEMU 下系统测试组通过，本用例各 7/7；日志里越界访问的信号是 11。
- 评审在最终提交 `40bdd3de86` 上的记录：`cargo xtask clippy --package starry-kernel` 13/13，`cargo xtask clippy --package ax-fs-ng` 7/7，`cargo xtask starry test qemu --arch x86_64 -c qemu-smp1/system/syscall-test-mmap-populate-eof` 7 通过、0 失败；CI 上 aarch64、riscv64、loongarch64 的 Starry QEMU 通过，x86_64 一项被工作流取消，红项是 Axvisor 的板级测试，与本改动无关。
