## 问题与原因

用户态缺页处理失败时，`new_user_task` 的循环在 `ReturnReason::PageFault` 分支里用 `SignalInfo::new_kernel(Signo::SIGSEGV)` 构造信号。这个构造函数只填 `si_signo` 与 `si_code = SI_KERNEL`，其余字段为零，所以 `SA_SIGINFO` 处理函数读到的 `si_addr` 恒为 0，`si_code` 也不是 `SEGV_MAPERR` 或 `SEGV_ACCERR`。故障地址就在该分支的 `addr` 里，只是没有传进信号。

按故障地址决定如何恢复的程序因此无法工作：处理函数分不清故障落在保护页、只读页还是空指针附近。

## 改动与影响范围

| 修改点 | 位置 | 内容 |
|:--:|:--:|:--:|
| `SEGV_MAPERR`、`SEGV_ACCERR` | `starry-signal/src/types.rs` | 新增常量，值为 1、2 |
| `SignalInfo::new_fault(signo, code, fault_addr)` | 同上 | 新增构造函数：清零后写 `si_signo`、`si_code`，并把地址写进 `_sifields._sigfault._addr` |
| `ReturnReason::PageFault` 分支 | `kernel/src/task/user.rs` | 持地址空间锁调用 `handle_page_fault`；失败后 `find_area(addr)` 命中记 `SEGV_ACCERR`，否则记 `SEGV_MAPERR`；改用 `new_fault(SIGSEGV, si_code, addr)` 投递；日志由 `info!` 改为 `warn!` |

影响范围：四个架构上由用户态缺页产生的 `SIGSEGV`（改动在架构无关的 `task/user.rs`）。`Exception` 分支产生的 `SIGBUS`、`SIGILL`、`SIGTRAP` 仍用 `new_kernel`，`si_addr` 仍为 0。

与 Linux 的差异：

- 分类。Linux 先找 VMA：找不到是 `SEGV_MAPERR`，找到而权限不符是 `SEGV_ACCERR`，权限相符才进入 `handle_mm_fault()`；后者失败时按返回值分三种处理：内存不足交给 OOM 处理、不发 `SIGSEGV`，`VM_FAULT_SIGBUS` 发 `SIGBUS`（`BUS_ADRERR`，例如文件映射访问到文件末尾之后），`VM_FAULT_SIGSEGV` 发 `SEGV_MAPERR`。补丁只在 `handle_page_fault` 返回失败之后看地址上有没有 VMA。合入时的 `handle_page_fault` 在权限相符而后端填充页失败（返回错误或填充了 0 页）时同样返回失败，这类故障于是被记成 `SEGV_ACCERR`。
- `SIGBUS`。补丁的缺页路径不产生 `SIGBUS`。
- `sigcontext.cr2`。Linux 在 x86 上发信号前把故障地址记进 `thread.cr2`，建信号帧时写入 `sigcontext.cr2`；补丁没有涉及。

当前 dev：两个常量与 `new_fault` 在 `os/StarryOS/signal/src/types.rs`（第 21、23、424 行）。缺页分支抽成 `handle_user_page_fault`（`os/StarryOS/kernel/src/task/user.rs` 第 24 行），分类不再用 `find_area`，改由 `handle_page_fault_result` 返回的 `FaultResult`（`mm/aspace/vma.rs` 第 35 行）给出：`PermissionDenied` 对 `SEGV_ACCERR`，`Unmapped` 对 `SEGV_MAPERR`，`Sigbus(code)` 发 `SIGBUS`，`NoMemory` 不发信号；发出的 `SIGSEGV` 与 `SIGBUS` 都经 `new_fault` 带上故障地址。`Misaligned`、`Breakpoint`、`IllegalInstruction` 仍用 `new_kernel`（`task/user.rs` 第 411 至 422 行）。x86_64 信号帧里的 `cr2` 仍写 0（`os/StarryOS/signal/src/arch/x86_64.rs` 第 110 行）。

## 溯源复核

- PR 标题只说 `SIGSEGV`，正文多处写「`SIGSEGV` / `SIGBUS`」，「影响」一节称同步 `SIGSEGV`/`SIGBUS` 都获得了符合 POSIX 的语义。合入的 diff 只改缺页分支，且固定发 `SIGSEGV`，没有任何路径产生带 `si_addr` 的 `SIGBUS`。回归用例给 `SIGBUS` 也装了处理函数，但两个子例触发的都是 `SIGSEGV`。以 diff 为准。
- 正文称故障分类「与 Linux `do_user_addr_fault()` 的语义一致」。只有「无 VMA」与「有 VMA 而权限不符」两种情况一致；权限相符而填充页失败的情况被记成 `SEGV_ACCERR`，Linux 对应的是 `SIGBUS`、`SEGV_MAPERR` 或交给 OOM 处理，见上文。这一点在当前 dev 上已由 `FaultResult` 的细分改掉。
- 回归用例只断言 `si_addr`，没有断言 `si_code`，`SEGV_MAPERR` 与 `SEGV_ACCERR` 的取值没有回归覆盖。
- 正文以 HotSpot JVM 为例，称 `si_addr` 恒为 0 会使它在近空指针偏移（`NULL + 0x34`）上误判，或在同一条指令上反复进入处理函数。这一因果没有附证据。三天后 [#1366](pr-1366.md) 的正文把同一现象（x86_64 上满屏的 `VA:0x34`）归因于新任务的 x87 标记字初值，说的是 musl 的 `fmt_fp` 越界清零了 `%fs:0`。本地记录（`notes/91-comprehensive-state-0619.md`）记的是：加上本补丁后 `0x34` 处的故障消失，Java 用例转为卡死。两种解释各自对应哪一次运行，没有留下可以区分的证据，待核实。本补丁作为 `si_addr` 语义的修复有独立的回归用例，不依赖这段解释。

## man 原文

[sigaction(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/sigaction.2?h=man-pages-6.19#n468)：

> SIGILL, SIGFPE, SIGSEGV, SIGBUS, and SIGTRAP fill in si_addr with the address of the fault.

[sigaction(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/sigaction.2?h=man-pages-6.19#n738)：

> The following values can be placed in si_code for a SIGSEGV signal: SEGV_MAPERR Address not mapped to object. SEGV_ACCERR Invalid permissions for mapped object.

## 验证

- `test-si-addr-sigsegv`：以 `SA_SIGINFO | SA_NODEFER` 给 `SIGSEGV` 与 `SIGBUS` 装处理函数，触发两类故障并断言 `si_addr` 等于故障地址：读地址 `0x34`；写一页 `PROT_READ` 的匿名映射。
- PR 正文：修复前两例的 `si_addr` 都是 0，打印 `SIADDR_FAIL`，退出码非 0；修复后打印 `SIADDR_OK 2/2`。宿主 Linux 上同一用例输出 `SIADDR_OK 2/2`。
- 评审记录（ZR233）：宿主 Linux 上以 `-std=c11 -Wall -Wextra -Werror -O0` 编译运行得 `SIADDR_OK 2/2`；`cargo xtask clippy --package starry-signal` 通过，`cargo xtask clippy --package starry-kernel` 的 17 组特性检查通过；CI 中 StarryOS x86_64 QEMU 运行到该用例并输出 `SIADDR_OK 2/2`，四个架构的 StarryOS 测试通过。唯一失败的 `Test axvisor self-hosted x86_64 / run_host`（`smoke-vmx` 超时）按既有的 #1230 归类。
- 当前 dev 上用例仍在，位置是 `test-suit/starryos/qemu/system/c-regression-test-si-addr-sigsegv`。
