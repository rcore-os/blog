## 问题与原因

loongarch64 的静态平台 `ax-plat-loongarch64-qemu-virt` 不看 QEMU 实际给了多少内存。`MemIf::phys_ram_ranges()` 直接由编译期常量 `LOW_MEMORY_SIZE`、`HIGH_MEMORY_BASE`、`PHYS_MEMORY_SIZE` 拼出两段内存返回，`_start` 把传给 `call_main` 的第二个参数写死为 0，旁边留着 `TODO: parse dtb`。QEMU 的 `-m` 再大，内核能用的也只有常量那么多。PR 正文说需要较多内存的应用因此只在 loongarch64 上内存耗尽，其他三个架构正常。

## 改动与影响范围

| 修改点 | 位置 | 内容 |
|:--:|:--:|:--:|
| `_start` | `src/boot.rs` | 入口处先把 `$a0` 至 `$a3` 存进 `$s0` 至 `$s3`；开启 MMU、切换栈之后调用 `set_fdt_ptr()` 把四个值交给内存模块，然后照旧以 `(cpuid, 0)` 进入 `call_main` |
| `set_fdt_ptr()`、`BOOT_REGS` | `src/mem.rs` | 只保存四个整数，不解引用 |
| `try_fdt_at()` | 同上 | 地址必须落在 `[0x1000, LOW_MEMORY_SIZE)` 且按 4 字节对齐；经启动期直映射窗口（`PHYS_BOOT_OFFSET`）读 4 字节，大端值须为 `0xd00dfeed`；再交给 `fdt_raw::Fdt::from_ptr` 解析，收集 `/memory` 节点里长度非零的区间，最多 8 个 |
| `detect_ram()` | 同上 | 依次尝试：四个寄存器值；在 `[0, 0x20_0000)` 内每 8 字节试一次；都不成则回退到原来由常量拼出的布局 |
| `phys_ram_ranges()` | 同上 | 改为返回 `detect_ram()` 的结果，用 `LazyInit` 缓存 |
| `phys-memory-size` | `axconfig.toml` | 由 `0x800_0000`（128 MiB）改为 `0x2000_0000`（512 MiB），只在找不到 FDT 时使用 |
| `fdt-raw` | `Cargo.toml` | 新增工作区依赖 |

影响范围：使用这个静态平台的 loongarch64 QEMU 目标，内核看到的可分配物理内存由 FDT 决定；找不到 FDT 时回退值也从 128 MiB 变成 512 MiB。保留区间、MMIO 区间与其他架构不变。loongarch64 的系统测试组改以 2 GiB 内存运行。

与 Linux 的差异：

- Linux 不扫描内存找 FDT。LoongArch 的入口约定是 `a0` 为 EFI 启动标志、`a1` 为命令行指针、`a2` 为 EFI 系统表指针；FDT 的地址从系统表的配置表里按 `DEVICE_TREE_GUID` 取得。
- Linux 在 ACPI 系统上不解析 FDT，内存信息来自 EFI 内存映射；只有非 ACPI 系统才扫描 FDT 的内存节点。
- Linux 认内存节点的条件是 `device_type` 为 `memory` 且节点可用，优先取 `linux,usable-memory`，其次 `reg`。补丁用的是 `fdt-raw` 的 `memory()`，它的判定条件没有核对。

当前 dev：这个平台已不存在。#1428（`chore(platforms): remove LoongArch static platform`，`59843144bc`，2026-06-30）删除了 `platforms/ax-plat-loongarch64-qemu-virt`，当前 `platforms/` 下只有 `ax-plat`、`ax-plat-macros`、`axplat-dyn`、`someboot`、`somehal`、`somehal-macros`，树里搜不到 `detect_ram`、`set_fdt_ptr`、`BOOT_REGS`。维护者 2026-06-12 在本 PR 下已说明 loongarch 改走动态平台、这个静态平台即将废弃。补丁的代码在 dev 上存在了两周。

## 溯源复核

- 四个寄存器里没有 FDT 指针。补丁注释与 PR 正文都写「QEMU 把 FDT 的物理指针放在 `$a0` 至 `$a3` 之一，具体哪一个随版本和引导路径而变」。按 QEMU v10.2.0 的源码，直接引导内核时 `a0 = 1`、`a1` 是命令行地址、`a2` 是它构造的 EFI 系统表地址，FDT 固定放在 `0x100000` 并登记进系统表的配置表，这与 Linux 的入口约定一致。`detect_ram()` 的第一步在这种情况下不会命中，实际找到 FDT 的是第二步的低地址扫描。其他 QEMU 版本没有核对。
- PR 正文说原来硬编码的是 512 MiB。diff 显示这个平台自己的 `axconfig.toml` 原值是 128 MiB，512 MiB 是本补丁改成的回退值，补丁在 `axconfig.toml` 里加的注释也写着「was 128M」。StarryOS 构建时实际生效的值是否另有覆盖，没有核对，待核实。
- 分支名 `fix-sys-getcpu` 与内容无关。评审机器人 2026-06-11 的第一份意见记录了当时 PR 处于关闭状态、分支名与内容不符、依赖还是 `fdt-parser`；本地记录说明这个 PR 原先承载的是与 #924 重复的 `getcpu` 改动，关闭后改为承载本改动，依赖也换成了工作区的 `fdt-raw`。
- 当前 dev 上被修改的平台已删除，见上文。

## man 原文

平台启动代码的改动，不涉及系统调用，无对应 man 条目。回归用例观察的是 `/proc/meminfo` 的 `MemTotal`，见 [proc_meminfo(5)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man5/proc_meminfo.5?h=man-pages-6.19#n33)：

> MemTotal %lu Total usable RAM (i.e., physical RAM minus a few reserved bits and the kernel binary code).
