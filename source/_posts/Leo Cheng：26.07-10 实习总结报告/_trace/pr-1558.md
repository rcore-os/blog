## 问题与原因

两处互不相关的问题，PR 正文说都是在 StarryOS 上跑源码交叉编译的 Envoy（higress）时暴露的，其中 `comm` 这一处只在链接 musl 的构建上出现。

**`/proc/<pid>/comm` 带 NUL 填充。** 读处理函数先分配 16 字节的零缓冲，填入名字（至多 15 字节）与一个换行，然后把 16 字节全部返回，名字短于 15 字节时换行后面跟着若干个 NUL。musl 的 `pthread_getname_np()` 对非当前线程读 `/proc/self/task/<tid>/comm`，把读到的最后一个字节置 0 来去掉换行；读到的是 16 字节时，被置 0 的是填充，换行留在名字里。PR 正文说 Envoy 的线程命名在设置后回读比对，比对失败使 worker 线程中止。

**`O_NONBLOCK` 套接字上的部分发送返回 `EAGAIN`。** `TcpSocket::send` 循环调用 smoltcp 的 `send`，每一步的结果交给 `finish_tcp_send_step` 判断是继续等待还是返回。这个函数由 #1533 引入，第三个参数表示「是否非阻塞」，调用处传的是 `extra_nb`，也就是只看本次调用有没有 `MSG_DONTWAIT`。套接字自身设了 `O_NONBLOCK` 而调用没带 `MSG_DONTWAIT` 时，某一步只写进一部分数据，函数按阻塞语义返回 `WouldBlock` 表示「还没发完，继续等」；外层的 `send_poller_with` 却认 `O_NONBLOCK`，不等待，直接把 `WouldBlock` 交给调用者。这时已有一部分字节从用户缓冲区取走并进了发送队列，调用者拿到 `EAGAIN` 后重发整段，流里出现重复数据。正文描述的现象是 HTTP/1.1 分块响应错位，大响应体在约 79KB 处截断。

## 改动与影响范围

| 修改点 | 位置 | 内容 |
|:--:|:--:|:--:|
| `comm` 的读处理 | `pseudofs/proc.rs`，`ThreadDir` | 改为只返回名字的前 `min(len, 15)` 字节加一个换行，长度为 `copy_len + 1` |
| `TcpSocket::send` | `ax-net/src/tcp.rs` | 新增 `let nonblocking = self.general.nonblocking() \|\| extra_nb;`，传给 `finish_tcp_send_step` 的第三个参数由 `extra_nb` 改为它 |

影响范围：读 `/proc/<pid>/comm` 与 `/proc/<pid>/task/<tid>/comm`；设了 `O_NONBLOCK` 的 TCP 套接字上的 `send`、`sendto`、`sendmsg`、`write`。阻塞套接字与带 `MSG_DONTWAIT` 的调用行为不变。`comm` 的写处理没有改。

与 Linux 的差异：

- `comm` 的读结果与 Linux 相同，都是名字加一个换行。截断的位置不同：Linux 在设置名字时就截到 15 字节，这里在读的时候截，输出没有区别。
- `comm` 的写处理（本补丁未改）不检查调用者与目标是否同属一个线程组。Linux 的 `comm_write()` 在不同线程组时返回 `EINVAL`。当前 dev 上仍是这样。

当前 dev：

- `comm` 的读处理没有变，在 `os/StarryOS/kernel/src/pseudofs/proc.rs` 第 1564 至 1580 行。
- `finish_tcp_send_step` 与 `TcpSocket::send` 里的那个循环已经不存在。发送路径重写为：内核侧 `Socket::send_from_user`（`os/StarryOS/kernel/src/file/net.rs` 第 98 行）取等待策略后调用 `wait_socket_io`，每次尝试走 `TcpSocket::try_send`（`net/ax-net/src/tcp.rs` 第 614 行），后者只做一步，要么返回写进队列的字节数，要么在一个字节都没写时返回 `WouldBlock`。「是否非阻塞」统一在 `socket_wait_policy` 里算（`net/ax-net/src/socket.rs` 第 257 至 274 行），取值是 `nonblocking || extra_nonblocking`，与本补丁的规则相同。

## 溯源复核

- 回归用例里的 `test_pthread_setname_roundtrip` 没有走到被修的读路径。用例对 `pthread_self()` 调用 `pthread_getname_np()`；musl 对当前线程走 `prctl(PR_GET_NAME)`，只有目标不是当前线程时才读 `/proc/self/task/<tid>/comm`。用例注释称这一项复现「Envoy's real path」，实际上它在修复前的内核上也会通过。评审记录里回退两处修复后的结果是 38 条通过、3 条失败。按用例代码推算，旧实现下失败的是 `test_comm_read_format` 里 `envoy`、`worker_0` 两个短名字的长度断言（各自连带跳过两条内层断言）与 `test_nonblocking_partial_send` 的「返回值大于 0」，合计 3 条失败、4 条未执行，45 减 4 正好是 41，与记录相符；`test_pthread_setname_roundtrip` 的 9 条都通过。对 `comm` 读格式真正起作用的是 `test_comm_read_format`。
- 评审第一轮对 TCP 这一处的要求是：断言 `send` 返回已发送的正字节数，并且对端收到的数据没有重发、没有重复。合入的用例只断言了返回值（大于 0 且小于请求长度），没有在接收端读回比对。
- 该用例已不在当前 dev 上，被 #2404（`test(starry): migrate bugfix and syscall probes to LTP`）删除，树里没有同名用例。
- PR 正文没有写验证结果，下文「验证」里的数字都出自评审记录。正文里关于 glibc 的 `pthread_getname_np` 返回 `ERANGE` 的说法没有核对，待核实。

## man 原文

[proc_pid_comm(5)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man5/proc_pid_comm.5?h=man-pages-6.19#n12)：

> /proc/pid/comm (since Linux 2.6.33) This file exposes the process's comm value—that is, the command name associated with the process. Different threads in the same process may have different comm values, accessible via /proc/pid/task/tid/comm. A thread may modify its comm value, or that of any of other thread in the same thread group (see the discussion of CLONE_THREAD in clone(2)), by writing to the file /proc/self/task/tid/comm. Strings longer than TASK_COMM_LEN (16) characters (including the terminating null byte) are silently truncated.

[send(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/send.2?h=man-pages-6.19#n167)：

> MSG_DONTWAIT (since Linux 2.2) Enables nonblocking operation; if the operation would block, EAGAIN or EWOULDBLOCK is returned. This provides similar behavior to setting the O_NONBLOCK flag (via the fcntl(2) F_SETFL operation), but differs in that MSG_DONTWAIT is a per-call option, whereas O_NONBLOCK is a setting on the open file description (see open(2)), which will affect all threads in the calling process as well as other processes that hold file descriptors referring to the same open file description.

[send(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/send.2?h=man-pages-6.19#n331)：

> On success, these calls return the number of bytes sent. On error, -1 is returned, and errno is set to indicate the error.

## 验证

- `bug-proc-comm-tcp-partial-send` 的三组断言：
  - `test_comm_read_format`：`prctl(PR_SET_NAME)` 设名后读 `/proc/self/comm`，断言读到的长度恰为名字长度加 1、内容相同、以一个换行结尾；名字取 `envoy`、`worker_0`、15 个字符的边界值，以及 20 个字符（期望截到 15）。
  - `test_pthread_setname_roundtrip`：`pthread_setname_np` 后 `pthread_getname_np` 读回相同，见「溯源复核」。
  - `test_nonblocking_partial_send`：回环上建一条 TCP 连接，发送端只用 `fcntl(F_SETFL, O_NONBLOCK)`，逐字节发到返回 `EAGAIN`，接收端读走一部分，`poll` 等到可写后一次发 1MiB，断言返回值大于 0 且小于 1MiB。
- 评审记录（ZR233）：第一轮指出两处修复都没有带回归用例，现有的 `finish_tcp_send_step` 单元测试直接传布尔值，不经过 `TcpSocket::send` 读 `O_NONBLOCK` 的分支，回退修复后仍会通过。补上用例后的复审结论：在 x86_64 上临时回退两处修复，同一条命令稳定得到 38 条通过、3 条失败；恢复后 45 条通过、0 条失败，并输出 `STARRY_GROUPED_TESTS_PASSED`。定向 clippy 通过，`ax-net` 2 组、`starry-kernel` 21 组。
- CI：唯一失败的是覆盖率作业的制品上传步骤（HTTP 500，error 1101），测试命令本身已跑完，评审把它归到 #1671。
- PR 的过程：7 月 13 日因为没有回归用例先行关闭，补上用例后重新打开，7 月 22 日合入。
- 当前 dev 上该用例已删除，见「溯源复核」。
