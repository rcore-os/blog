## 问题与原因

procfs 的 `builder()` 没有注册 `/proc/filesystems`，`/proc/sys` 下只有 `kernel` 一个子目录。读取下列路径的程序得到 `ENOENT`：`/proc/filesystems`、`/proc/sys/vm/overcommit_memory`、`/proc/sys/vm/max_map_count`、`/proc/sys/fs/file-max`、`/proc/sys/fs/nr_open`、`/proc/sys/net/core/somaxconn`。PR 正文举的读者是 Elasticsearch 与部分 JVM 的启动预检（`max_map_count`）、读取系统上限的服务端程序、`mount` 与 `findmnt`（`/proc/filesystems`），没有附具体的失败记录。

## 改动与影响范围

全部用现有的 `SimpleFile::new_regular` 加静态字符串实现，只读，没有状态。

| 路径 | 内容 |
|:--:|:--:|
| `/proc/filesystems` | `nodev\tsysfs`、`nodev\tproc`、`nodev\ttmpfs`、`nodev\tdevtmpfs`、`\text4` 五行 |
| `/proc/sys/vm/overcommit_memory` | `0` |
| `/proc/sys/vm/max_map_count` | `65530` |
| `/proc/sys/fs/file-max` | `1048576` |
| `/proc/sys/fs/nr_open` | `1048576` |
| `/proc/sys/net/core/somaxconn` | `4096` |

影响范围：只影响读这些路径的 `open`/`read`，不改变任何系统调用的行为。

与 Linux 的差异：这些文件在 Linux 里是可写的 sysctl（模式 0644），值由内核实际使用；这里是常量字符串，既不可写，也不反映或约束内核的行为。

当前 dev：六个文件都在 `pseudofs/proc.rs`（`filesystems` 第 1985 行，`overcommit_memory` 第 2165 行，`max_map_count` 第 2169 行，`file-max` 第 2179 行，`nr_open` 第 2183 行，`somaxconn` 第 2249 行），内容未变。`max_map_count` 改由 `unsupported_limit_sysctl_file` 构造，读仍返回 `65530`，写返回 `EOPNOTSUPP`，该函数的注释写明内核并不执行这个限制。

## 溯源复核

- `/proc/filesystems` 的内容是写死的，与内核实际支持的挂载类型不同步。Linux 遍历已注册的文件系统类型逐行输出。合入时 `sys_mount` 还接受 `devpts` 与 `cgroup2`，列表里没有；`ext4` 受 `#[cfg(feature = "ext4")]` 控制，列表里无条件列出。当前 dev 的 `sys_mount` 又增加了 `ramfs`、`overlay`，列表仍是这五行。评审者提过在注释里说明需要同步维护，属于非阻塞建议，合入的 diff 里没有加。
- `file-max` 的 `1048576` 不是 Linux 的固定默认值。Linux 在启动时按物理内存计算 `files_stat.max_files`，下限为 `NR_FILE`；`1048576` 是 `nr_open` 的默认值。PR 正文把两者都称为「常见 Linux 默认」，对 `file-max` 不准确。其余四个值与对照版本的默认值一致。

## man 原文

[proc_filesystems(5)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man5/proc_filesystems.5?h=man-pages-6.19#n16)：

> /proc/filesystems A text listing of the filesystems which are supported by the kernel, namely filesystems which were compiled into the kernel or whose kernel modules are currently loaded. (See also filesystems(5).) If a filesystem is marked with "nodev", this means that it does not require a block device to be mounted (e.g., virtual filesystem, network filesystem).

[proc_sys_vm(5)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man5/proc_sys_vm.5?h=man-pages-6.19#n250)：

> /proc/sys/vm/overcommit_memory This file contains the kernel virtual memory accounting mode. Values are: 0: heuristic overcommit (this is the default)

[proc_sys_fs(5)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man5/proc_sys_fs.5?h=man-pages-6.19#n104)：

> /proc/sys/fs/file-max This file defines a system-wide limit on the number of open files for all processes. System calls that fail when encountering this limit fail with the error ENFILE.

[proc_sys_fs(5)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man5/proc_sys_fs.5?h=man-pages-6.19#n237)：

> /proc/sys/fs/nr_open (since Linux 2.6.25) This file imposes a ceiling on the value to which the RLIMIT_NOFILE resource limit can be raised (see getrlimit(2)). This ceiling is enforced for both unprivileged and privileged process. The default value in this file is 1048576.

[listen(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/listen.2?h=man-pages-6.19#n124)：

> If the backlog argument is greater than the value in /proc/sys/net/core/somaxconn, then it is silently capped to that value. Since Linux 5.4, the default in this file is 4096; in earlier kernels, the default value is 128.

man-pages 6.19 的 proc_sys_vm(5) 没有 `max_map_count` 的条目。

## 验证

- `test-procfs-sysctl`：`/proc/filesystems` 可读且含 `ext4`；`overcommit_memory` 可读且解析为非负整数；`max_map_count`、`file-max`、`nr_open`、`somaxconn` 可读且解析为正整数。用例不固定具体数值，在 Linux 宿主上同样成立；修复前这些路径是 `ENOENT`，各条断言都会失败。
- 这个用例是维护者以「补充测试」为由要求补的。维护者最终批准时写明，当前提交的 CI（run `27070151997`）在 x86_64、aarch64、riscv64、loongarch64 四个架构的 Starry QEMU 任务上通过。PR 正文只写了 x86_64 内核编译通过，没有给断言数量。
- 当前 dev：用例在 `test-suit/starryos/qemu/system/syscall-test-procfs-sysctl`，断言未变。
