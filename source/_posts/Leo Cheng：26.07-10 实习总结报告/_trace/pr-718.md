## 问题与原因

进程的「可转储」属性（dumpable）完全缺失：`prctl(PR_GET_DUMPABLE)` 与 `prctl(PR_SET_DUMPABLE)` 返回 `EINVAL`，身份变化后也不会把属性清零。依赖它的程序会走错分支：服务进程降权后用 `PR_SET_DUMPABLE(0)` 防止核心转储泄露内存内容，uid/gid 测试套件的 `core_dump_inhibit` 系列用例因此只能跳过。Linux 把这个属性放在 `mm_struct` 的标志位里，在 `commit_creds()` 发现有效编号或文件系统编号变化时重置为 `suid_dumpable`（默认 0），fork 时随 `mm` 标志一起继承。

## 改动与影响范围

| 修改点 | 位置 | 内容 |
|:--:|:--:|:--:|
| `ProcessData::dumpable` | `task/mod.rs` | 新增 `AtomicI32` 字段，初值 1（`SUID_DUMP_USER`），附读写函数 |
| `PR_GET_DUMPABLE` / `PR_SET_DUMPABLE` | `syscall/task/ctl.rs` | 读返回当前值；写只接受 0 与 1，其余 `EINVAL` |
| `maybe_clear_dumpable_on_euid_change()` | `syscall/sys.rs` | 有效编号变化时把属性清零；`setuid`、`setresuid`、`setreuid` 三处调用 |
| `setfsuid` / `setfsgid` | `syscall/sys.rs` | 文件系统编号实际变化时同样清零（评审补充） |
| fork/clone | `syscall/task/clone.rs` | 子进程继承父进程的值，而不是回到 1 |

影响范围：进程级的一个整数属性，读者只有 `prctl` 本身；StarryOS 当时没有核心转储与 `ptrace` 附加检查，所以这一属性不改变别的子系统的行为，只让用户态读到的值与 Linux 一致。属性放在 `ProcessData` 上而不是 `mm` 上，在一个进程一个地址空间的前提下等价。

合入时与 Linux 仍有三处差异，现状如下：

| 差异 | Linux | 合入时 | 当前 dev |
|:--:|:--:|:--:|:--:|
| 有效组编号变化 | `commit_creds()` 同样重置 | 未处理 | 已补：#1674（Josen-B，2026-07-27）引入 `dumpable_should_reset()`，覆盖 euid、egid、fsuid、fsgid |
| 权能集合扩大 | `cred_cap_issubset()` 为假时重置 | 未处理 | 仍未处理，StarryOS 的权能只由有效编号是否为 0 推出 |
| execve | 普通程序重置为 1，设置了 set-user-ID 的程序重置为 `suid_dumpable` | 未处理 | 仍未处理，`execve` 路径没有写这个属性 |

正文「Round N+1 已修 egid」一句与合入的差异不符：合入的提交只在 euid 与 fsuid/fsgid 路径上清零。这里以合入的差异为准。

## 代码对照

### `prctl` 的读写分支

合入前 `sys_prctl` 没有 `PR_GET_DUMPABLE` 与 `PR_SET_DUMPABLE` 两个分支，`ProcessData` 上也没有这个属性。

Linux（[kernel/sys.c#L2567-L2576](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/kernel/sys.c#L2567-L2576)）：

```c
	case PR_GET_DUMPABLE:
		error = get_dumpable(me->mm);
		break;
	case PR_SET_DUMPABLE:
		if (arg2 != SUID_DUMP_DISABLE && arg2 != SUID_DUMP_USER) {
			error = -EINVAL;
			break;
		}
		set_dumpable(me->mm, arg2);
		break;
```

本 PR（`os/StarryOS/kernel/src/syscall/task/ctl.rs`，当前 dev 上两个分支都在，错误类型换成 `StarryError::InvalidInput`）：

```rust
PR_GET_DUMPABLE => {
    // man 2 prctl PR_GET_DUMPABLE: returns current dumpable value
    // (0=SUID_DUMP_DISABLE, 1=SUID_DUMP_USER, 2=SUID_DUMP_ROOT).
    return Ok(current().as_thread().proc_data.dumpable() as isize);
}
PR_SET_DUMPABLE => {
    // ...
    if arg2 != 0 && arg2 != 1 {
        return Err(AxError::InvalidInput);
    }
    current().as_thread().proc_data.set_dumpable(arg2 as i32);
}
```

### 身份变化时清零

合入前（`os/StarryOS/kernel/src/syscall/sys.rs`，`sys_setuid` 的结尾，提交凭据时不动别的状态）：

```rust
new.fsuid = new.euid;
thread.set_cred(new);
Ok(0)
```

Linux（[kernel/cred.c#L381-L389](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/kernel/cred.c#L381-L389)，`commit_creds()`）：

```c
	/* dumpability changes */
	if (!uid_eq(old->euid, new->euid) ||
	    !gid_eq(old->egid, new->egid) ||
	    !uid_eq(old->fsuid, new->fsuid) ||
	    !gid_eq(old->fsgid, new->fsgid) ||
	    !cred_cap_issubset(old, new)) {
		if (task->mm)
			set_dumpable(task->mm, suid_dumpable);
		task->pdeath_signal = 0;
```

本 PR（同一文件，只比较一对编号；`sys_setresuid`、`sys_setreuid` 的结尾加了同样的一行，`sys_setfsuid`、`sys_setfsgid` 在文件系统编号变化时也调用它）：

```rust
fn maybe_clear_dumpable_on_euid_change(old_euid: u32, new_euid: u32) {
    if old_euid != new_euid {
        current().as_thread().proc_data.set_dumpable(0);
    }
}
// ...
new.fsuid = new.euid;
maybe_clear_dumpable_on_euid_change(old.euid, new.euid);
thread.set_cred(new);
Ok(0)
```

当前 dev（`os/StarryOS/kernel/src/syscall/sys.rs`，#1674 换成 `dumpable_should_reset()`，比较有效与文件系统的用户、组四个编号）：

```rust
fn dumpable_should_reset(old: &crate::task::Cred, new: &crate::task::Cred) -> bool {
    old.euid != new.euid || old.egid != new.egid || old.fsuid != new.fsuid || old.fsgid != new.fsgid
}
// ...
new.fsuid = new.euid;
let reset_dumpable = dumpable_should_reset(&old, &new);
commit_cred_with_id_rules(thread, new);
if reset_dumpable {
    thread.proc_data.set_dumpable(0);
}
Ok(0)
```

## man 原文

[PR_SET_DUMPABLE(2const)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2const/PR_SET_DUMPABLE.2const?h=man-pages-6.19#n26)：

> dumpable must be either 0L (SUID_DUMP_DISABLE, process is not dumpable) or 1L (SUID_DUMP_USER, process is dumpable).
>
> Normally, the "dumpable" attribute is set to 1. However, it is reset to the current value contained in the file /proc/sys/fs/suid_dumpable (which by default has the value 0), in the following circumstances:
>
> - The process's effective user or group ID is changed.
> - The process's filesystem user or group ID is changed (see credentials(7)).
> - The process executes (execve(2)) a set-user-ID or set-group-ID program, resulting in a change of either the effective user ID or the effective group ID.
> - The process executes (execve(2)) a program that has file capabilities (see capabilities(7)), but only if the permitted capabilities gained exceed those already permitted for the process.

[PR_SET_DUMPABLE(2const)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2const/PR_SET_DUMPABLE.2const?h=man-pages-6.19#n81)：

> EINVAL arg2 is neither SUID_DUMP_DISABLE nor SUID_DUMP_USER.

[setuid(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/setuid.2?h=man-pages-6.19#n141)：

> If uid is different from the old effective UID, the process will be forbidden from leaving core dumps.

## 验证

- uid/gid 测试套件 B、C、D 三组的 `core_dump_inhibit` 用例：`PR_GET_DUMPABLE` 默认 1、`PR_SET_DUMPABLE(0)` 持久、`PR_SET_DUMPABLE(2)` 返回 `EINVAL`、三种 setuid 改变有效编号后读到 0。正文记录复刻仓库持续集成 `pass=18 fail=0 skipping=30`。
- fork 继承：正文记录在 Linux 宿主上核对过「父进程置 0 后 fork，子进程读到 0」。
