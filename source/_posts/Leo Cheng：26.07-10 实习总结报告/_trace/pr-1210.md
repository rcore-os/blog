## 问题与原因

`handle_syscall` 的分派表里只有 `Sysno::prlimit64`，没有 `Sysno::getrlimit` 与 `Sysno::setrlimit`，这两个系统调用落到默认分支，返回 `ENOSYS`。musl 的 `getrlimit()` 包装内部用的是 `prlimit64`，所以经 libc 调用的程序不受影响；直接发旧系统调用号的程序会失败。PR 正文举的例子是 Go 的 `syscall` 包：consul 在 riscv64 上启动时因 `getrlimit` 返回 `ENOSYS` 而 `SIGABRT`。

## 改动与影响范围

| 修改点 | 位置 | 内容 |
|:--:|:--:|:--:|
| `Sysno::getrlimit` | `syscall/mod.rs` 的 `handle_syscall` | 转为 `sys_prlimit64(0, resource, null, rlim)`，即只取旧值 |
| `Sysno::setrlimit` | 同上 | 转为 `sys_prlimit64(0, resource, rlim, null)`，即只设新值 |

`pid` 传 0 表示当前进程。用户态的 `struct rlimit` 是两个 `unsigned long`，在四个 64 位架构上与 `struct rlimit64` 的两个 `u64` 布局相同，所以直接把指针交给 `sys_prlimit64`，没有另做转换。`prlimit64` 自己的分支未动。

影响范围：四个架构上的 `getrlimit`、`setrlimit` 两个系统调用号（x86_64 为 97、160，其余三个架构为 163、164）。参数校验、权限判断、各资源的取值都是 `sys_prlimit64` 原有的行为。

与 Linux 的差异：loongarch64 的 Linux 不提供这两个系统调用，补丁在该架构上也返回成功，见「溯源复核」。

当前 dev：两个分支仍在 `syscall/mod.rs` 第 1021 至 1034 行，多了一个 `current` 参数，其余未变；上方的注释（第 1011 至 1020 行）也原样保留。

## 溯源复核

- 补丁注释与 PR 正文对 aarch64 的说法不对。二者都写「aarch64 与 loongarch64 的 Linux 走 asm-generic，对这两个号返回 `ENOSYS`，补丁在这两个架构上是更宽松的超集」。对照版本里，通用系统调用表把 163、164 标为 `rlimit` 这一组，各架构在 `Makefile.syscalls` 里声明自己启用哪些组：arm64 的 64 位表启用了 `rlimit`，riscv 的 64 位表也启用了，loongarch 没有。因此 aarch64 的 Linux 提供 `getrlimit` 与 `setrlimit`，补丁在 aarch64 上是补齐缺失，不是多给；只有 loongarch64 才是 Linux 返回 `ENOSYS` 而补丁返回成功。当前 dev 的注释仍是原文。
- 回归用例在 loongarch64 上断言的是与 Linux 相反的结果：它要求原始的 `getrlimit` 返回 0，而 loongarch64 的 Linux 对这个号返回 `ENOSYS`。用例没有按架构区分。

## man 原文

[getrlimit(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/getrlimit.2?h=man-pages-6.19#n415)：

> The Linux-specific prlimit() system call combines and extends the functionality of setrlimit() and getrlimit(). It can be used to both set and get the resource limits of an arbitrary process.

[getrlimit(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/getrlimit.2?h=man-pages-6.19#n606)：

> Since glibc 2.13, the glibc getrlimit() and setrlimit() wrapper functions no longer invoke the corresponding system calls, but instead employ prlimit(), for the reasons described in BUGS.
>
> The name of the glibc wrapper function is prlimit(); the underlying system call is prlimit64().

## 验证

- `syscall-test-getrlimit-legacy`（8 条断言）用 `syscall()` 直接发旧系统调用号：`getrlimit(RLIMIT_NOFILE)` 返回 0 且软限制不大于硬限制；结果与 `prlimit64` 取到的一致；`setrlimit` 把软限制设为硬限制后返回 0，`prlimit64` 能看到新值；`getrlimit(RLIMIT_STACK)` 返回 0；最后用 `setrlimit` 还原。
- PR 正文：x86_64、aarch64、riscv64、loongarch64 单核 QEMU 下各 8/8。
- 评审记录的 CI：格式、clippy、sync-lint 通过；aarch64、loongarch64 的 Starry QEMU 通过；x86_64 与 riscv64 两项里本用例都是 8 通过、0 失败，x86_64 那一项的失败点是已有的 `bug-tcp-concurrent-connect`，与本改动无关，riscv64 那一项随后被取消。
- 评审指出用例里 `SYS_getrlimit`、`SYS_setrlimit` 的缺省定义 163、164 对 x86_64 不成立；musl 的头文件在四个架构上都定义了这两个宏，缺省分支不生效。合入时未改。
- 当前 dev 仍保留这个用例，位置是 `test-suit/starryos/qemu/system/syscall-test-getrlimit-legacy`。
