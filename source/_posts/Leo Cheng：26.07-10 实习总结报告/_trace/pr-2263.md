## 问题与原因

`sys_times` 填 `struct tms` 与返回值时用了两种都不对的单位：四个字段写的是 `Duration::as_micros()`（微秒），返回值是 `nanos_to_ticks(monotonic_time_nanos())`（硬件定时器的计数）。`times(2)` 的四个字段与返回值都以时钟节拍计，每秒的节拍数由 `sysconf(_SC_CLK_TCK)` 给出，Linux 上是 `USER_HZ`，即 100。用户态按 100 去除，得到的秒数差出几个数量级。

PR 正文在 x86_64 QEMU 上对未修改的内核实测：`_SC_CLK_TCK` 为 100；睡眠约 300 毫秒，返回值增加 995507456（应约为 30）；忙循环之后 `tms_utime + tms_stime` 为 699366（应约为 70）。

撞上的是所有按 `_SC_CLK_TCK` 换算 `times()` 结果的程序。

## 改动与影响范围

| 修改点 | 内容 |
|:--:|:--:|
| `sys_times` 的四个字段 | 新增闭包 `ticks = \|d\| (d.as_millis() / 10) as usize`，`tms_utime`、`tms_stime`、`tms_cutime`、`tms_cstime` 都经它换算 |
| `sys_times` 的返回值 | 由 `nanos_to_ticks(monotonic_time_nanos())` 改为 `monotonic_time().as_millis() / 10` |
| 导入 | 去掉不再使用的 `monotonic_time_nanos`、`nanos_to_ticks` |

`as_millis() / 10` 先截到毫秒再除以 10，结果等于纳秒数整除 10^7，与 Linux 的 `nsec_to_clock_t`（除以 `NSEC_PER_SEC / USER_HZ`）一致。同一换算在 `task/stat.rs` 里已经用于 `/proc/[pid]/stat` 的 `utime`、`stime` 等字段，补丁沿用它。

影响范围：只有 `times(2)`。四个字段的数据来源没有改：补丁时 `tms_utime`、`tms_stime` 取自当前线程的 `time.borrow().output()`，`tms_cutime`、`tms_cstime` 取自 `proc_data.children_cpu_time()`。

当前 dev：`sys_times` 在 `syscall/time.rs` 第 263 行，换算闭包在第 271 行，返回值在第 281 行，与补丁相同。数据来源后来变了，见下一节。

## 溯源复核

- 补丁只改了单位，没有改统计范围。Linux 的 `do_sys_times` 用 `thread_group_cputime_adjusted` 取整个线程组的用户态与内核态时间；补丁时的 `sys_times` 读的是调用线程自己的计时，多线程进程里 `tms_utime`、`tms_stime` 只含调用线程的份额。#1775（2026-09-08 合入）把它改为 `proc_data.cpu_time()`，即进程内全部线程之和（`task/process_accounting.rs` 第 153、154 行），这一点已与 Linux 一致。
- `times(NULL)` 与 Linux 不同，补丁没有涉及，当前 dev 也没有改。Linux 在 `tbuf` 为空时跳过回写，照常返回节拍数。`sys_times` 无条件对 `tms` 做 `vm_write`，没有空指针分支，`times(NULL)` 的结果取决于地址 0 能否写入，写不进去就经 `?` 返回错误，而不是返回节拍数。这一条只读了代码，没有在 QEMU 上实测。
- 用例的上界很宽：返回值增量只要求落在 `[1, 30 * clk]`，CPU 时间只要求不超过 `100 * clk`。按 PR 正文的实测值，它能把微秒（699366）和硬件计数（995507456）判为失败，但若单位是毫秒（约 700 与约 300）同样会通过。它证明的是「不再是微秒或硬件计数」，没有把单位钉在 10 毫秒。
- 第二轮自动评审留了一条未处理的建议：用例只检查 `tms_utime + tms_stime`，没有创建并回收子进程，`tms_cutime`、`tms_cstime` 的单位没有被断言。
- 用例已不在当前 dev 上：#2404（2026-09-14 合入）删除了 `bugfix-times-clock-ticks` 的两个文件。

## man 原文

[times(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/times.2?h=man-pages-6.19#n75)：

> All times reported are in clock ticks.

[times(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/times.2?h=man-pages-6.19#n77)：

> times() returns the number of clock ticks that have elapsed since an arbitrary point in the past.

[times(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/times.2?h=man-pages-6.19#n176)：

> The number of clock ticks per second can be obtained using: sysconf(_SC_CLK_TCK);

[times(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/times.2?h=man-pages-6.19#n41)：

> The tms_utime field contains the CPU time spent executing instructions of the calling process. The tms_stime field contains the CPU time spent executing inside the kernel while performing tasks on behalf of the calling process.

[times(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/times.2?h=man-pages-6.19#n94)：

> On Linux, the buf argument can be specified as NULL, with the result that times() just returns a function result. However, POSIX does not specify this behavior, and most other UNIX implementations require a non-NULL value for buf.

返回值的起点手册只说是「过去某个任意时刻」，StarryOS 取开机时刻，不构成差异。

## 验证

- `bugfix-times-clock-ticks`：断言 `sysconf(_SC_CLK_TCK) == 100`；两次 `times()` 之间睡眠约 300 毫秒，断言返回值增量在 `[1, 30 * clk]` 内；忙循环两亿次之后，断言 `tms_utime + tms_stime` 大于 0 且不超过 `100 * clk`。
- PR 正文：该用例修复前失败、修复后通过，修复前的实测值见「问题与原因」。正文没有给出修复后的数值与断言数。
- 评审记录（自动评审）：第一轮指出 CPU 时间为零时字段断言被打印成 `SKIP` 而不计失败、`_SC_CLK_TCK` 出错时被静默换成 100，要求修改；改为 `check(cpu > 0, ...)` 与 `check(clk == 100, ...)` 后批准。批准时 head `23897d70` 的 39 项检查全部成功。
