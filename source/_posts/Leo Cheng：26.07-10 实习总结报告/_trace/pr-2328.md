## 问题与原因

aarch64 的 QEMU 上，往串口一次写入较长的命令，只回显前一部分，之后的输入也不再推进。

`Pl011Irq::handle()` 的顺序是：读 `UARTMIS`，把接收 FIFO 读空，最后把读到的状态整个写进 `UARTICR`。最后一次判断 FIFO 为空之后、写 `UARTICR` 之前到达的字节，它的接收中断位被这次写一并清掉。QEMU 的 PL011 只在 FIFO 水位越过触发点的那一刻置位接收中断，清掉之后不会按当前水位重新计算。结果是 FIFO 里有数据、接收中断已使能，却没有待处理的中断，接收从此停住。

## 改动与影响范围

| 修改点 | 内容 |
|:--:|:--:|
| 发送中断 | 采样到发送中断时先屏蔽它，再往下处理 |
| 写 `UARTICR` | 提到读 FIFO 之前，并且不含接收与接收超时两位；这两位靠读 `UARTDR` 消退 |
| 读 FIFO | 不变，一次最多读 `IRQ_RX_BATCH_CAPACITY` 个 |
| 末尾 | 删掉原来的 `uarticr.set(active)`；读满一批或有溢出时仍屏蔽接收，由运行时重新使能 |

影响范围：用 PL011 的平台，即 QEMU 的 aarch64 `virt` 机器与使用该驱动的板子。当前 dev 上 `drivers/serial/some-serial/src/pl011/irq.rs` 的 `handle()` 就是这个版本，用例 `serial-rx` 也在。

与 Linux 的差异：Linux 的 `pl011_int()` 写 `UARTICR` 时同时排除发送位，发送中断靠往 `UARTDR` 写数据消退；补丁先屏蔽发送中断再清它的状态位，之后由运行时重新使能。Linux 在一次中断里循环重读状态直到为零；补丁每次中断只处理一轮。

## 溯源复核

- 这个 PR 的提交有三个。第一个是提交者的：把写 `UARTICR` 整体提到读 FIFO 之前，同时为了测试把寄存器操作抽成 `Pl011IrqOps`，配一个假的 `FakePl011`。维护者 `ZR233` 09.09 的意见是：修的是真实串口停收，假设备的 FIFO 与中断语义由测试自己定义，不能代替真实设备；测试专用的抽象不该留在生产代码里。之后他在同一分支上追加了两个提交：删掉 `Pl011IrqOps` 与 `FakePl011`，把清除改成排除接收两位的写法，并加上真实的 QEMU 回归 `serial-rx`。合入的驱动改动与回归用例出自这两个提交。
- 维护者同时开过 #2359 修同一处，开了十几分钟后关闭，改为并入本 PR。
- 「QEMU 只在水位越过触发点时置位、清除后不重新计算」这一点来自 PR 正文与用例说明，没有对 QEMU 源码逐行核对；用例里的现象（晚到字节的 `UARTMIS.RX` 已置位，旧实现随后超时）与这个说法一致。
- PR 正文记有一处没解决的问题：用 Firefox 应用实跑时，串口不再停收，但约 24 秒后在 `components/ax-task/src/sync/mutex/mod.rs` 触发 `validate PI mutex blocking context failed` 的 panic。这与串口无关，本 PR 没有处理。

## 验证

数字取自 PR 正文。

- `serial-rx` 走生产的 `TaskConsoleInput::read()`，要求活动控制台是带中断的 PL011。宿主经独占的 TCP 串口与 QEMU 的 GDB 接口控制时机：先送 63 字节，用 MMIO 读观察点数 `UARTDR` 的读取次数，在已判断 FIFO 为空、即将读 `UARTRSR` 时停住，注入第 64 字节并确认 `UARTMIS.RX` 已置位，再恢复执行。第一批收齐后宿主再发 30 字节，验证后续接收仍然工作。
- 把 `handle()` 恢复成先读空再清状态：晚到字节的 `UARTMIS.RX` 置位后接收超时，外层退出码 1。
- 修复后 `cargo xtask arceos test qemu --test-group rust --test-case serial-rx --arch aarch64`：两个阶段通过，退出码 0。
- 故意改错第二批的预期首字节：`serial phase 2, byte 0` 断言失败，退出码 1。
- `cargo xtask clippy --package some-serial --package axbuild --package arceos-test-suit` 45 项通过；`cargo xtask test --since abff1a38` 13 个受影响的软件包通过。变基到 dev `51637235` 后 clippy 44 项通过，`serial-rx` 再次通过。
- 合入前的 CI 上 `ArceOS / QEMU aarch64 · GICv2 SMP4 boot + suites` 通过。
