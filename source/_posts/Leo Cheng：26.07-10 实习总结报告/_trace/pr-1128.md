## 问题与原因

aarch64 上的用户程序在 EL0 执行 `MRS Xt, ID_AA64*_EL1` 读 CPU 特性寄存器时被 `SIGILL` 杀死。这类寄存器只能在 EL1 读，EL0 的读取以 `ESR_EL1.EC == 0`（Unknown）陷入内核；StarryOS 把这一类异常归为 `ExceptionKind::IllegalInstruction`，`task/user.rs` 的用户异常分派对它直接取 `Signo::SIGILL` 并发致命信号（diff 中被替换的那一行）。Linux 在同一条路径上先尝试模拟这条指令，模拟不了才发 `SIGILL`。

PR 正文举的例子是静态链接的 arm64 `juicefs`：`juicefs version` 在 Go 运行时探测 CPU 特性时即 `SIGILL`。

## 改动与影响范围

| 修改点 | 位置 | 内容 |
|:--:|:--:|:--:|
| `UserContext::emulate_mrs_id_reg()` | `components/axcpu/src/aarch64/uspace.rs` | 新增。从 `elr` 指向的地址读 4 字节指令，按 `(insn & 0xFFF0_0000) == 0xD530_0000` 判定为 `MRS`，解出 `op0`、`op1`、`CRn`、`CRm`、`op2`、`Rt`；命中下表的编码时把结果写入 `x[Rt]`（`Rt` 为 31 时丢弃），`elr` 加 4，返回 `true`；其余返回 `false` |
| 异常分派 | `os/StarryOS/kernel/src/task/user.rs` 的 `new_user_task` | `IllegalInstruction` 分支在 aarch64 上先调用 `emulate_mrs_id_reg()`，成功则跳出异常处理回到用户态，否则仍发 `SIGILL` |

各编码的返回值，与 Linux 对照：

| 编码 | 补丁返回 | Linux 返回 |
|:--:|:--:|:--:|
| `ID_AA64PFR0_EL1` | 当前 CPU 的寄存器值与 `0x00FF_FFFF`：`EL0`、`EL1`、`EL2`、`EL3`、`FP`、`AdvSIMD` 六个字段原样，其余为 0 | `FP`、`AdvSIMD`、`DIT` 可见，`SVE` 在 `CONFIG_ARM64_SVE` 下可见；`EL0`、`EL1` 固定为安全值 `IMP`（1），`EL2`、`EL3` 与其余字段为 0 |
| `ID_AA64ISAR0_EL1` | 原样 | 除 `TLB`（59:56）外的字段可见 |
| `ID_AA64ISAR1_EL1` | 清掉 `APA`（7:4）、`API`（11:8）、`GPA`（27:24）、`GPI`（31:28），其余原样 | 除 `XS`（59:56）、`SPECRES`（43:40）外的字段可见；四个指针认证字段在 `CONFIG_ARM64_PTR_AUTH` 下可见 |
| `ID_AA64MMFR0_EL1` | 原样 | 只有 `ECV` 可见，其余字段取特性表里的安全值 |
| `ID_AA64MMFR1_EL1` | 原样 | 只有 `AFP` 可见 |
| `ID_AA64MMFR2_EL1` | 原样 | 只有 `AT` 可见 |
| `op0=3, op1=0, CRn=0, CRm=4..7` 的其余编码 | 0 | 有特性表的寄存器按表返回，没有特性表的返回 0 |
| `CRm` 为 0（`MIDR_EL1`、`MPIDR_EL1`、`REVIDR_EL1`）、2、3 | 不模拟，`SIGILL` | 模拟 |

Linux 返回的可见字段取自 `sys_val`，即各 CPU 之间取安全值后的系统级结果；补丁读的是执行这条指令时所在 CPU 的寄存器。

影响范围：aarch64 上所有在 EL0 读 `ID_AA64*_EL1` 的程序。调用点带 `#[cfg(target_arch = "aarch64")]`，其他架构不变；不是这类 `MRS` 的未定义指令仍得到 `SIGILL`。

当前 dev：这段逻辑在 `os/StarryOS/kernel/src/task/user_cpu_features.rs` 第 8 行的 `emulate_mrs_id_reg(current, context)`，该文件首次出现在 #2363 的合入提交 `822a34a6c9`（2026-09-11）。两个掩码与 `match` 的各分支未变；寄存器改经 `ax_cpu::capability::IdRegister`（`components/axcpu/src/arch/aarch64/capability.rs` 第 58 行）读取；指令改经 `UserConstPtr::<u32>::read` 读取，读不到时返回 `false`。调用点在 `task/user.rs` 第 419 行。

## 溯源复核

- PR 正文没有随评审更新。正文写的是「读取真实寄存器，写入 Xt」，也没有提回归用例。首版确实原样返回九个寄存器，第二轮评审指出不能把 EL1 的原始值交给用户态，合入的 diff 已改成上表的掩码与归零，并补了 `test-mrs-idreg`。以 diff 为准。
- 返回值不是 Linux 的用户可见视图，两个方向都有差异。多暴露的：`ID_AA64MMFR0_EL1`、`ID_AA64MMFR1_EL1`、`ID_AA64MMFR2_EL1` 整个原样返回，Linux 各只暴露一个字段；`ID_AA64PFR0_EL1` 的 `EL0` 至 `EL3` 原样返回，Linux 对这四个字段给固定值；`ID_AA64ISAR0_EL1.TLB`、`ID_AA64ISAR1_EL1.XS`、`ID_AA64ISAR1_EL1.SPECRES` 原样返回，Linux 隐藏。少暴露的：`ID_AA64PFR0_EL1.DIT` 被掩掉；`ID_AA64PFR1_EL1`、`ID_AA64ISAR2_EL1`、`ID_AA64ISAR3_EL1` 等在 Linux 里有可见字段的寄存器一律读到 0；指针认证四个字段恒为 0。补丁注释里「as Linux's `emulate_mrs` also avoids」只对 `PFR0` 高位与 `ISAR1` 的指针认证字段成立。评审在通过时已写明这不是完整复刻 `arm64_ftr_reg_user_value()`。当前 dev 未改。
- `ID_AA64DFR0_EL1` 在 Linux 上读到的不是 0。Linux 的特性表把它的字段全部标为隐藏，隐藏字段取安全值，其中 `DebugVer` 的安全值是 `0x6`，所以 EL0 读到 `0x6`。补丁返回 0，回归用例断言 `dfr0 == 0`；同一断言在 Linux 上不成立。用例检查的是 StarryOS 自己的掩码策略，不是与 Linux 的一致性。
- `MIDR_EL1`、`MPIDR_EL1`、`REVIDR_EL1` 以及 `CRm` 为 2、3 的编码没有模拟，EL0 读取仍是 `SIGILL`。Linux 的模拟范围是 `CRm` 为 0 与 2 至 7。当前 dev 未改。
- Linux 有两个入口，补丁只接了一个。除了 `EC == 0` 走 `do_el0_undef()`，Linux 在 `EC == 0x18`（`ESR_ELx_EC_SYS64`）的 `do_el0_sys()` 里还有一个钩子处理同一类读取。StarryOS 的 `ExceptionInfo::kind()` 只把 `Unknown` 与 `IllegalExecutionState` 归为 `IllegalInstruction`（当前 dev 的 `components/axcpu/src/arch/aarch64/uspace.rs` 第 269 至 279 行），`EC == 0x18` 落入 `Other`，得到 `SIGTRAP`。哪些 CPU 会以 `0x18` 上报这类读取：按 Arm 架构对 `ID_AA64MMFR2_EL1.IDS`（FEAT_IDST）的定义应是实现了该特性的 CPU，这一条没有挂上可核对的链接，待核实。
- 合入版本用 `core::ptr::read(self.tf.elr as *const u32)` 直接解引用用户地址取指令，不经过用户内存访问的检查；Linux 用 `get_user()`，读失败按 `SIGILL` 处理。同一进程的另一个线程在陷入之后解除该页映射时，合入版本会在内核态缺页。当前 dev 已改为经 `UserConstPtr` 读取。
- Linux 用 `AT_HWCAP` 里的 `HWCAP_CPUID` 向用户态声明这套接口可用。当前 dev 的 `elf_hwcap()`（`os/StarryOS/kernel/src/cpu_capabilities.rs`）在 aarch64 上返回 0，没有置这一位；先查 `HWCAP_CPUID` 再读寄存器的程序不会用到这段模拟。

## man 原文

不涉及系统调用，无对应 man 条目。这套用户态接口由内核文档定义：[Documentation/arch/arm64/cpu-feature-registers.rst#L8-L10](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/Documentation/arch/arm64/cpu-feature-registers.rst?plain=1#L8-L10)：

> This file describes the ABI for exporting the AArch64 CPU ID/feature registers to userspace. The availability of this ABI is advertised via the HWCAP_CPUID in HWCAPs.

[Documentation/arch/arm64/cpu-feature-registers.rst#L102-L111](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/Documentation/arch/arm64/cpu-feature-registers.rst?plain=1#L102-L111)：

> The following rules are applied to the value returned by the infrastructure:
>
> a) The value of an 'IMPLEMENTATION DEFINED' field is set to 0.
> b) The value of a reserved field is populated with the reserved value as defined by the architecture.
> c) The value of a 'visible' field holds the system wide safe value for the particular feature (except for MIDR_EL1, see section 4).
> d) All other fields (i.e, invisible fields) are set to indicate the feature is missing (as defined by the architecture).
