## 问题与原因

`starry-signal` 取待处理信号时按信号号从小到大：`PendingSignals::dequeue_signal` 调 `SignalSet::dequeue`，后者用 `trailing_zeros` 取最低位。`ThreadSignalManager` 在返回用户态前取信号的循环先取线程队列、再取进程队列，都是这个次序。于是同一线程上由缺页产生的 `SIGSEGV`（11）与另一线程用 `tgkill` 送来的 `SIGUSR1`（10）同时待处理时，`SIGUSR1` 先被投递到用户处理函数。

Linux 在这种情况下先投递 `SIGSEGV`，为的是让信号栈帧里保存的指令指针指向出错的那条指令。PR 正文说，此前仓库里的 `test-fault-pending-signal` 靠给 `SIGUSR1` 的突发个数设上界才能通过，没有真正的次序保证。

## 溯源复核

补丁只移植了 Linux 两处同步信号优先逻辑中的一处，并且移植的这一处有两点与 Linux 不同。

- Linux 的普通出队本身就偏向同步信号。`next_signal()` 对信号集的第一个字（64 位上是 1 至 64 号）先看有没有未屏蔽的 `SYNCHRONOUS_MASK` 信号，有就只在这六个里取最小号，不看 `si_code`。`dequeue_signal()` 经 `__dequeue_signal()` 调它，`get_signal()`、`do_sigtimedwait()` 与 signalfd 的读取都走 `dequeue_signal()`。因此在 Linux 上，同一队列里 `SIGUSR1` 与 `SIGSEGV` 同时待处理时，`sigtimedwait` 先返回 `SIGSEGV`；用户用 `kill` 发来的 `SIGSEGV` 也排在同队列的 `SIGHUP` 之前。补丁没有改 `SignalSet::dequeue`，这两种情况在 StarryOS 上仍按信号号从小到大。当前 dev 未改。
- PR 正文与 `dequeue_deliverable` 的注释称保持 `dequeue_signal` 的「纯最小号优先」与 Linux 一致，理由是 Linux 只在 `get_signal()` 里调用 `dequeue_synchronous_signal()`。后半句属实，但 Linux 的 `dequeue_signal()` 不是纯最小号优先（见上一条）。第二个单测 `user_sent_synchronous_signal_is_not_prioritized` 断言 `dequeue_signal` 先取 `SIGHUP`、后取用户发来的 `SIGSEGV`，这个次序与 `next_signal()` 的结果相反。
- Linux 的 `dequeue_synchronous_signal()` 只查当前线程的私有队列 `tsk->pending`，不查进程共享队列。补丁多查了一层进程级队列。Linux 上同步故障总是定向发给出错的线程，所以常见路径上没有差别；差别出现在进程级队列里有 `si_code` 为正的这六种信号时，StarryOS 会让它越过线程队列里的其他信号。
- Linux 取的是队列里按入队先后的第一个符合条件的条目，补丁取信号号最小的那个。两个同步故障同时待处理（例如先 `SIGSEGV` 后 `SIGBUS`）时次序不同。`pending.rs` 的注释把「最小号优先」归到 `next_signal()` 名下，那是另一个函数的行为。
- PR 正文列举的 QEMU 证据是既有用例 `test-fault-pending-signal` 在四个架构上通过。这个用例没有随 PR 修改，突发上界（`POST_READY_SIGUSR1_BURST`）在当前 dev 上还在，它在补丁之前也能通过，不构成「修复前失败、修复后通过」的证据。能区分新旧行为的只有两个单测。

## man 原文

[signal(7)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man7/signal.7?h=man-pages-6.19#n435)：

> If multiple standard signals are pending for a process, the order in which the signals are delivered is unspecified.

手册不保证标准信号之间的投递次序，同步信号优先是 Linux 实现的行为，依据只在源码里。
