## 问题与原因

loongarch64 上浮点与向量密集的程序在信号或抢占下崩溃：gradle/kotlin 编译器（HotSpot）`SIGSEGV`（#237），Alpine 的 numpy 以 LSX 为基线、拒绝导入。三处缺陷互相牵连，必须一起修：只通告 LSX 而不保存它，用户态的 LSX 运算会被信号或切换破坏，比不通告更糟。

1. 平台启动即打开 128 位 LSX（`EUEN.SXE`），但 `FpuState` 只存 `f0`–`f31` 的低 64 位，切换或信号打断后 `vr[127:64]` 丢失。
2. 信号投递只保存通用寄存器；异步信号（HotSpot 安全点的 `SIGSEGV`）打断浮点代码后，`sigreturn` 用处理函数留下的浮点值恢复。另外 musl 的 loongarch64 `ucontext_t` 在 `uc_sigmask` 与 `uc_mcontext` 之间有 8 字节 `__uc_pad`，缺了它 `uc_mcontext` 提前 8 字节，处理函数读写的寄存器全部错位。
3. ELF 加载器从不发 `AT_HWCAP`，`getauxval(AT_HWCAP)` 为 0，numpy 按 `HWCAP_LOONGARCH_LSX` 判断后拒绝导入。

## 改动与影响范围

| 修改点 | 位置 | 内容 |
|:--:|:--:|:--:|
| `FpuState::fp_high` | `axcpu/loongarch64/context.rs` | 新增 32 个 64 位槽保存 `vr[127:64]`；`fp` 布局不变，只读标量的代码不受影响 |
| `SAVE_FP_HIGH` / `RESTORE_FP_HIGH` | `axcpu/loongarch64/macros.rs` | 只存取每个向量寄存器的高 64 位：保存用 `vstelm.d`，恢复用 `ld.d` 加 `vinsgr2vr.d`；低 64 位仍由原有的标量路径保存 |
| `MContext::fpu` | `starry-signal/arch/loongarch64.rs` | 投递时保存现场浮点与向量状态，`sigreturn` 时恢复 |
| `UContext::__uc_pad` | 同上 | 在 `sigmask` 与 `mcontext` 之间补 8 字节 |
| `hwcap_value()` 与辅助向量 | `mm/loader.rs` | loongarch64 报 `CPUCFG|LAM|UAL|FPU|LSX`，不报 LASX（未开 `EUEN.ASXE`）；其他架构报 0 |

影响范围：loongarch64 的任务切换与信号帧，以及所有架构的辅助向量多了一项 `AT_HWCAP`（非 loongarch 取 0，与此前缺失时 `getauxval` 的返回值相同）。

与 Linux 的差异：Linux 把浮点与 LSX 状态放在 `sc_extcontext` 之后，每块带魔数头（`FPU_CTX_MAGIC`、`LSX_CTX_MAGIC`），用户态可按魔数解析；本拉取请求把 `FpuState` 原样放在该位置，只供内核恢复，按魔数读取扩展上下文的用户程序（调试器、少数运行时）读不到。x86_64 与 aarch64 的 `AT_HWCAP` 报 0 也与 Linux 不同，Linux 在这两个架构上报告实际特性位。

当前 dev：`fp_high` 在 `components/axcpu/src/arch/loongarch64/fp.rs`，`__uc_pad` 与 `MContext::fpu` 在 `os/StarryOS/signal/src/arch/loongarch64.rs`，特性位移到 `os/StarryOS/kernel/src/cpu_capabilities.rs`。

### 保存 LSX 的高 64 位

合入前（`components/axcpu/src/loongarch64/context.rs`，`FpuState` 里每个寄存器只有 64 位）：

```rust
pub struct FpuState {
    /// Floating-point registers (f0-f31)
    pub fp: [u64; 32],
    /// Floating-point Condition Code register
    pub fcc: [u8; 8],
```

Linux（[arch/loongarch/kernel/fpu.S#L371-L377](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/arch/loongarch/kernel/fpu.S#L371-L377)）：

```asm
/*
 * Save a thread's LSX vector context.
 */
SYM_FUNC_START(_save_lsx)
	lsx_save_all	a0 t1 t2
	jr	ra
SYM_FUNC_END(_save_lsx)
```

本 PR（同一文件，新增 `fp_high`，`save_fp_registers` 在 `SAVE_FP` 之后接着存高半部分；当前 dev 上 `fp_high` 在 `components/axcpu/src/arch/loongarch64/fp.rs`，06.09 合入的 #1178 又加了 LASX 的两组槽）：

```rust
pub struct FpuState {
    /// Low 64 bits of the vector registers `vr0`-`vr31` (the scalar `f0`-`f31`).
    pub fp: [u64; 32],
    /// High 64 bits of the vector registers `vr0`-`vr31` (`vr[127:64]`).
    ///
    /// Saved/restored via LSX so an async signal (or preemptive switch)
    /// interrupting a thread mid-LSX-op does not clobber these on resume.
    pub fp_high: [u64; 32],
// ...
SAVE_FP $a0
addi.d $t8, $a0, {fp_high_offset}
SAVE_FP_HIGH $t8
```

本 PR（`components/axcpu/src/loongarch64/macros.rs`，`SAVE_FP_HIGH` 与 `RESTORE_FP_HIGH` 对 `vr0`–`vr31` 逐个展开这两个宏）：

```asm
.macro SAVE_VR_HIGH vd, base_reg, off
    vstelm.d \vd, \base_reg, \off, 1
.endm
.macro RESTORE_VR_HIGH vd, base_reg, off
    ld.d        $t0, \base_reg, \off
    vinsgr2vr.d \vd, $t0, 1
.endm
```

### 信号帧里 `uc_mcontext` 的偏移

合入前（`components/starry-signal/src/arch/loongarch64.rs` 的 `UContext`，`__unused` 之后紧跟 `mcontext`）：

```rust
pub stack: SignalStack,
pub sigmask: SignalSet,
__unused: [u8; 1024 / 8 - size_of::<SignalSet>()],
pub mcontext: MContext,
```

Linux（[arch/loongarch/include/uapi/asm/ucontext.h#L14-L33](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/arch/loongarch/include/uapi/asm/ucontext.h#L14-L33)）：

```c
struct ucontext {
	unsigned long		uc_flags;
	struct ucontext		*uc_link;
	stack_t			uc_stack;
	sigset_t		uc_sigmask;
	/* There's some padding here to allow sigset_t to be expanded in the
	 * future.  Though this is unlikely, other architectures put uc_sigmask
	 * at the end of this structure and explicitly state it can be
	 * expanded, so we didn't want to box ourselves in here. */
	__u8		  __unused[1024 / 8 - sizeof(sigset_t)];
	/* We can't put uc_sigmask at the end of this structure because we need
	 * to be able to expand sigcontext in the future.  For example, the
	 * vector ISA extension will almost certainly add ISA state.  We want
	 * to ensure all user-visible ISA state can be saved and restored via a
	 * ucontext, so we're putting this at the end in order to allow for
	 * infinite extensibility.  Since we know this will be extended and we
	 * assume sigset_t won't be extended an extreme amount, we're
	 * prioritizing this. */
	struct sigcontext	uc_mcontext;
};
```

本 PR（同一文件；当前 dev 上文件搬到 `os/StarryOS/signal/src/arch/loongarch64.rs`，这段仍在）：

```rust
pub stack: SignalStack,
pub sigmask: SignalSet,
__unused: [u8; 1024 / 8 - size_of::<SignalSet>()],
// musl loongarch64 `ucontext_t` has `long __uc_pad` between `uc_sigmask` and
// `uc_mcontext`; without it `mcontext` lands 8 bytes early and a userspace
// SIGSEGV handler reading/writing `uc_mcontext` (e.g. HotSpot advancing the
// saved PC / inspecting GPRs) corrupts the resumed register state.
__uc_pad: u64,
pub mcontext: MContext,
```

Linux（[arch/loongarch/include/uapi/asm/hwcap.h#L6-L11](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/arch/loongarch/include/uapi/asm/hwcap.h#L6-L11)）：

```c
#define HWCAP_LOONGARCH_CPUCFG		(1 << 0)
#define HWCAP_LOONGARCH_LAM		(1 << 1)
#define HWCAP_LOONGARCH_UAL		(1 << 2)
#define HWCAP_LOONGARCH_FPU		(1 << 3)
#define HWCAP_LOONGARCH_LSX		(1 << 4)
#define HWCAP_LOONGARCH_LASX		(1 << 5)
```

本 PR（同一文件，不报 LASX）：

```rust
const fn hwcap_value() -> usize {
    #[cfg(target_arch = "loongarch64")]
    {
        // Linux loongarch HWCAP bits (uapi/asm/hwcap.h):
        const HWCAP_LOONGARCH_CPUCFG: usize = 1 << 0;
        const HWCAP_LOONGARCH_LAM: usize = 1 << 1;
        const HWCAP_LOONGARCH_UAL: usize = 1 << 2;
        const HWCAP_LOONGARCH_FPU: usize = 1 << 3;
        const HWCAP_LOONGARCH_LSX: usize = 1 << 4;
        HWCAP_LOONGARCH_CPUCFG
            | HWCAP_LOONGARCH_LAM
            | HWCAP_LOONGARCH_UAL
            | HWCAP_LOONGARCH_FPU
            | HWCAP_LOONGARCH_LSX
    }
    #[cfg(not(target_arch = "loongarch64"))]
    {
        0
    }
}
// ...
auxv.push(AuxEntry::new(AuxType::HWCAP, hwcap_value()));
```

当前 dev（`os/StarryOS/kernel/src/cpu_capabilities.rs`，06.09 合入的 #1178 加了 LASX 位，函数现名 `elf_hwcap`，riscv64 另有取值）：

## Linux 依据

- 内核视角的 `ucontext`：`uc_sigmask` 后用 `__unused` 补到 128 字节，`uc_mcontext` 因 16 字节对齐落在 176：[arch/loongarch/include/uapi/asm/ucontext.h#L14-L33](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/arch/loongarch/include/uapi/asm/ucontext.h#L14-L33)；`sigcontext` 的 16 字节对齐成员 [arch/loongarch/include/uapi/asm/sigcontext.h#L20-L25](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/arch/loongarch/include/uapi/asm/sigcontext.h#L20-L25)

## man 原文

[getauxval(3)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man3/getauxval.3?h=man-pages-6.19#n95)：

> AT_HWCAP An architecture and ABI dependent bit-mask whose settings indicate detailed processor capabilities. The contents of the bit mask are hardware dependent (for example, see the kernel source file arch/x86/include/asm/cpufeature.h for details relating to the Intel x86 architecture; the value returned is the first 32-bit word of the array described there). A human-readable version of the same information is available via /proc/cpuinfo.
