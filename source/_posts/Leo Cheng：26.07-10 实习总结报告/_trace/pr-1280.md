## 问题与原因

loongarch64 的 `USER_SPACE_SIZE` 是 `0x3f_ffff_f000`，加上 `USER_SPACE_BASE`（`0x1000`）后用户地址空间的上界是 `0x40_0000_0000`（256 GiB）；`USER_STACK_TOP` 是 `0x4_0000_0000`（16 GiB）。`AddrSpace::validate_region` 对超出这个范围的映射请求返回 `NoMemory`（`address out of range`）。x86_64 与 aarch64 此前已是 128 TiB，只有 loongarch64 与 riscv64 还停在 256 GiB。

按 PR 正文，HotSpot 为 CompressedOops 堆基址做的高地址预留在 loongarch64 上落到 256 GiB 之上，被拒绝后 JVM 无限重试，多 JDK 的 Java 用例卡死。这一因果只有 PR 正文与补丁注释为据，没有附复现日志。

## 改动与影响范围

| 常量 | 改动前 | 改动后 |
|:--:|:--:|:--:|
| `USER_SPACE_SIZE` | `0x3f_ffff_f000`（上界 256 GiB） | `0x7fff_ffff_f000`（上界 `0x8000_0000_0000`，128 TiB） |
| `USER_STACK_TOP` | `0x4_0000_0000`（16 GiB） | `0x0400_0000_0000`（4 TiB） |

补丁注释给的依据是页表实现的能力：`page_table_multiarch` 的 `LA64MetaData` 为 4 级、48 位虚拟地址，低半区正好是 128 TiB。riscv64 是 Sv39，保持 256 GiB 不变。

影响范围：loongarch64 上所有用户进程的地址范围检查上界与初始栈位置。栈由 16 GiB 移到 4 TiB，栈顶之上约 124 TiB 留给映射。堆基址与信号跳板地址未动。

与 Linux 的差异：

- Linux 的 loongarch64 用户空间上界不是编译期常量，启动时从 CPUCFG1 读出虚拟地址位数，与页表配置能表示的位数取小。补丁写死 128 TiB，见「溯源复核」。
- Linux 把栈放在 `TASK_SIZE` 顶端（扣掉 vDSO 所占空间），映射区从 `TASK_SIZE / 3` 起向上找；补丁把栈放在 4 TiB，栈的上方留给映射，与 [#1114](pr-1114.md) 对 x86_64、aarch64 的做法相同。

当前 dev：两个常量改名为 `USER_SPACE_MAX_SIZE`（`config/loongarch64.rs` 第 11 行）与 `USER_STACK_TOP_MAX`（第 19 行），数值不变，含义变成上限。实际的用户地址范围由 `mm/layout.rs` 第 43 至 52 行用平台报告的范围与这两个上限取交集得到；loongarch64 平台的范围来自 CPUCFG（`platforms/someboot/src/arch/loongarch64/mod.rs` 第 227 至 230 行调用 `virtual_address.rs` 第 31 行的 `from_valen`）。`validate_region` 在 `mm/aspace/mod.rs` 第 2103 行，越界仍返回 `NoMemory`。

## 溯源复核

- 补丁把上界写死为 128 TiB，前提是 CPU 实现了 48 位虚拟地址。Linux 按 CPUCFG1 的实际值计算 `TASK_SIZE64`，位数较少的 CPU 得到较小的用户空间。这一差别后来在实体板卡上暴露：#1368（`bee2d2f15d`，2026-07-08，LS2K1000 板级支持）在同一文件加了 `loongarch64-low-va` 特性，注释写明 LS2K1000 只有 40 位虚拟地址，更高的地址在页表遍历之前就触发地址错误异常，该板的构建因此退回 256 GiB 窗口与 16 GiB 栈顶。#2261（`271565db91`，2026-09-05）删掉这个特性，改为运行时按 CPUCFG 裁剪，与 Linux 的做法一致。
- 回归用例对 riscv64 断言「1 TiB 处的 `MAP_FIXED` 必须失败」。这是 StarryOS 只用 Sv39 的实现限制，不是 Linux 的行为：Linux 的 riscv64 按启动时选定的页表模式（Sv39、Sv48 或 Sv57）决定 `TASK_SIZE`，在 Sv48 及以上的机器上同一调用会成功。
- 回归用例所在的 `syscall-test-mmap-family` 已不在当前 dev 的树里，见「验证」。

## man 原文

用户地址空间的大小没有对应的 man 条目。回归用例依赖的是 `MAP_FIXED` 的语义，[mmap(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/mmap.2?h=man-pages-6.19#n220)：

> MAP_FIXED Don't interpret addr as a hint: place the mapping at exactly that address.
>
> If the specified address cannot be used, mmap() will fail.

## 验证

- `syscall-test-mmap-family` 新增的断言：在 `0x10000000000`（1 TiB）以 `MAP_PRIVATE | MAP_ANONYMOUS | MAP_FIXED` 映射一页，x86_64、aarch64、loongarch64 上要求返回该地址，riscv64 上要求返回 `MAP_FAILED`。
- PR 正文：修复前 loongarch64 上这条断言失败，修复后通过；四个架构单核 QEMU 下系统测试组无回归；依赖本修复的多 JDK Java 用例在 loongarch64 上通过。正文没有给通过条数。
- 评审记录：合入前的 CI 上 `Check formatting`、`Run clippy` 与四个架构的 `Test starry ... qemu` 通过。
- 当前 dev 的树里已没有这个用例。目录后来移到 `test-suit/starryos/qemu/system/syscall-test-mmap-family`，由 #2404（`test(starry): migrate bugfix and syscall probes to LTP`，`1564626a04`，2026-09-14）整个删除。接替它的 `test-suit/starryos/qemu/system/ltp-syscalls/cases.txt` 里与 `mmap` 相关的条目是 `mmap01`、`mmap02`、`mmap06`；其中是否有条目覆盖高地址的 `MAP_FIXED`，没有逐条核对。
