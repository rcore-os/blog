## 问题与原因

#1566 的系统用例 `bugfix-bug-tun-tap-abi` 逐项检查 `/dev/net/tun` 的 ioctl 返回值与错误码，但没有一条完整的「用户态注入一个包、内核协议栈应答、应答从 fd 读回」的链路，也不在 `cargo xtask starry app qemu` 这条应用测试路径上。本 PR 补一个不依赖外部工具与第二个网络端点的应用级用例。

最初的版本只绑定 `IFF_TUN | IFF_NO_PI`，评审（ZR233，7 月 13 日）指出它在 TAP 仍按 IP 包收发、第二个 fd 被错误接受、`IFF_PERSIST` 生命周期出错时也会全部通过，标题里的「TUN/TAP」名不副实。后续几轮补上了 TAP 与生命周期，并修掉了用例自身的三个问题：`tap-carpet.c` 对 `inet_addr()` 的结果又调了一次 `htonl()`，小端机器上 ARP 目标地址被反转，内核不应答；x86_64 的 QEMU 配置写的是非 UEFI 启动，进不了客户机；失败时脚本输出的 `TEST FAILED (tun_rc=...)` 与整行匹配的失败正则对不上，要等到超时才结束。

## 改动与影响范围

内核侧的 15 个文件见 [#1566](pr-1566.md)，这里不重复。应用部分：

| 文件 | 内容 |
|:--:|:--:|
| `programs/tun-echo.c` | 打开 `/dev/net/tun`，`TUNGETFEATURES` 含 `IFF_TUN`，以 `IFF_TUN \| IFF_NO_PI` 创建 `tun0` 并用 `TUNGETIFF` 读回名字；用 `SIOCSIFADDR`、`SIOCSIFNETMASK`、`SIOCSIFFLAGS` 配成 `10.8.0.1/24` 并拉起。第一阶段向 fd 写入一个源地址 `10.8.0.2` 的 ICMP echo 请求，读回内核协议栈生成的应答，校验源目地址互换、id 与 seq、IPv4 与 ICMP 两层校验和。第二阶段向同网段另一主机发 6 字节 UDP 数据报，从 fd 读到这个出站包 |
| `programs/tap-carpet.c` | 以 `IFF_TAP \| IFF_NO_PI` 创建 `tcarp0`；`TUNGETIFF` 返回名字与两个标志；`SIOCGIFHWADDR` 的 MAC 非零、组播位为 0、本地管理位为 1；配成 `10.8.2.1/24` 并拉起后写入一个广播 ARP 请求帧，读回应答并校验以太网源目地址与 ARP 的发送方、目标方 MAC 和 IP。生命周期三组：非持久设备关闭后查询返回 `ENODEV` 且同名可以重建；`TUNSETPERSIST 1` 后关闭设备仍在，重新挂接后 MAC 不变，`TUNSETPERSIST 0` 并关闭后返回 `ENODEV`；单队列设备的第二个 fd 得到 `EBUSY` |
| `programs/run-tun-tap.sh` | 先确认 `/dev/net/tun` 是字符设备，再依次运行两个探针，返回码单独输出一行，最后单独一行输出 `TEST PASSED` 或 `TEST FAILED` |
| `prebuild.sh` | 用静态 musl 交叉编译两个探针并放进 overlay |
| `qemu-*.toml` | 四个架构都用 nvme 盘上的 alpine 根文件系统、`-smp 1`、`[[shell_check_steps]]`；x86_64 与 loongarch64 经 UEFI 启动；成功正则 `^TEST PASSED\s*$`，失败正则含 `^TEST FAILED\s*$` |

影响范围：不改变内核行为。新增一条应用测试 `cargo xtask starry app qemu -t tun-tap --arch <arch>`。

这组用例依赖的内核行为与 Linux 的对应关系：持久设备靠「重新挂接后 MAC 不变」来区分重新挂接与同名重建，Linux 上 TAP 的 MAC 在创建设备时随机生成，StarryOS 上由不复用的接口 id 派生，两边重建后都会得到不同的 MAC；MAC 的两个位断言在 Linux 上由 `eth_random_addr()` 保证，在 StarryOS 上由固定前缀 `02:00` 保证。

当前 dev：`apps/starry/tun-tap` 的 14 个文件都在，内容与合入时相同。

## 溯源复核

- 骨架列的「内核侧文件」与 `gh pr diff` 一致，但它们属于 #1566。本 PR 的净贡献没有内核代码，标题的 `test(tun-tap)` 是准确的。
- 9 月 15 日的自动评审把「`TUNSETPERSIST` 没有检查 `CAP_NET_ADMIN`」列为本 PR 唯一的阻塞项，并称 Linux 对该操作要求这项能力。按本文对照的 Linux 版本，`__tun_chr_ioctl()` 的 `TUNSETPERSIST` 分支里没有能力检查，进入该分支的前提只有文件已挂接到设备。评审的说法与源码不符，作者据此回复后未改，合入版与 Linux 一致。
- PR 正文写明删除了「`IFF_VNET_HDR` 返回 `EINVAL`」这条检查，理由是 Linux 支持该标志。用例不再断言这一点，但内核（#1566）对 `IFF_VNET_HDR` 仍返回 `EINVAL`，这是 #1566 列明的差异，本用例既不覆盖也不掩盖它。
- 这组用例不检查错误码的全集、权限、名字分配、带 PI 的读写、MTU 与 `poll`，这些在 `bugfix-bug-tun-tap-abi` 里；标题里的「carpet」指的是 TUN 三层收发、TAP 二层成帧与三种生命周期，README 的 Scope 一段已如实说明。

## man 原文

man-pages 6.19 没有 tun 或 tap 的条目。内核文档 [Documentation/networking/tuntap.rst#L27-L35](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/Documentation/networking/tuntap.rst#L27-L35)：

> In order to use the driver a program has to open /dev/net/tun and issue a corresponding ioctl() to register a network device with the kernel. A network device will appear as tunXX or tapXX, depending on the options chosen. When the program closes the file descriptor, the network device and all corresponding routes will disappear.
>
> Depending on the type of device chosen the userspace program has to read/write IP packets (with tun) or ethernet frames (with tap). Which one is being used depends on the flags given with the ioctl().
