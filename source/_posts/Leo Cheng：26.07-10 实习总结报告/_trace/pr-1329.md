## 问题与原因

合入前 `ExtendedState::save` 与 `restore` 分别是 `_fxsave64` 与 `_fxrstor64`，`TaskContext::switch_to` 每次切换都对换出的任务调用 `save`、对换入的任务调用 `restore`。FXSAVE 区只有 x87、MXCSR 与 XMM 寄存器，不含 YMM 的高 128 位。

[#1112](pr-1112.md) 让启动路径在 CPU 支持时置 `CR4.OSXSAVE` 并把 AVX 写进 `XCR0`，用户态从此可以执行 AVX 指令，但切换时 YMM 的高 128 位既不保存也不恢复：任务被换出再换回，高 128 位是这个 CPU 上别的任务留下的值，低 128 位完好。

撞上的条件是 CPU 型号带 XSAVE 与 AVX（系统测试组用的 `-cpu Haswell,+avx`），且有两个以上的任务交替使用 YMM 寄存器。按补丁注释，默认的 `qemu64` 型号没有 XSAVE，#1112 在这种型号上不开 AVX，不受影响。

## 改动与影响范围

| 修改点 | 内容 |
|:--:|:--:|
| `XsaveArea`（新增） | 1024 字节、64 字节对齐；前 512 字节是原有的 `FxsaveArea`，其后是 64 字节的 XSAVE 头与扩展区 |
| `ExtendedState` | 公开字段 `fxsave_area: FxsaveArea` 换成私有的 `area: XsaveArea`，另给只读方法 `fxsave_area()` |
| `xsave_enabled()`、`xsave_mask()`（新增） | 前者读 `CR4.OSXSAVE`，后者用 `XGETBV` 读 `XCR0` |
| `save()`、`restore()` | `CR4.OSXSAVE` 置位时用 `_xsave64`、`_xrstor64`，掩码取 `XCR0`；否则仍用 `_fxsave64`、`_fxrstor64`，读写同一块区域的前 512 字节 |
| `default()` | 整块清零，XSAVE 头的 `XSTATE_BV` 为 0，首次 `XRSTOR` 把各分量置为初始态；再写 `fcw = 0x37f`、`ftw = 0xffff`、`mxcsr = 0x1f80` |

影响范围：x86_64 上开启 `fp-simd` 特性后的所有任务切换。不涉及系统调用。`switch_to` 本身没有改，仍是每次切换保存一次、恢复一次。

与 Linux 的差异：

- 保存区大小。Linux 在启动时用 `CPUID.0DH` 取 XSAVE 区的实际大小；补丁写死 1024 字节，依据是启动路径只开 x87、SSE、AVX 三个分量（512 + 64 + 256 = 832 字节）。补丁里没有把 CPUID 报告的大小与 1024 做比较，启动路径一旦多开分量，`XSAVE` 会写出保存区之外。
- 掩码。Linux 保存时用任务的 `fpstate->xfeatures`，不读寄存器；补丁每次保存、恢复各读一次 `CR4` 与 `XCR0`。
- 时机。Linux 只在换出用户任务时保存（内核线程跳过），恢复推迟到返回用户态之前；补丁沿用原来的做法，不区分内核线程，换入时立即恢复。
- 指令。Linux 按 CPU 特性在 XSAVE、XSAVEOPT、XSAVEC、XSAVES 中择一；补丁只用 XSAVE。
- 初始态。Linux 的初始映像是先对全零头部执行 `XRSTOR`，再用 `FXSAVE` 读回 legacy 区；补丁手写 legacy 区的三个字段。其中 `ftw = 0xffff` 在 FXSAVE 回退路径上是错的，由 [#1366](pr-1366.md) 改正。

当前 dev：文件搬到 `components/axcpu/src/arch/x86_64/context.rs`。`XsaveArea` 改名为公开的 `UserXstate`（第 242 行），`XSAVE_AREA_SIZE` 仍是 1024（第 217 行）。`ExtendedState::save`、`restore`（第 506、537 行）保留了补丁的两条分支；`uspace` 特性下优先走一条新分支，掩码取每 CPU 初始化时缓存的 `XCR0`（`local_state.rs` 第 146、205 行），CPU 支持时改用 `_xsaveopt64`（第 518 行）。切换路径也改了：`prepare_switch_to`（第 693 行）只在当前任务持有 FPU 状态时保存，恢复推迟到返回用户态前的 `prepare_user_return_fp`（第 714 行）。`UserXstate::user_size()`（第 264 行）断言 `CPUID.0DH` 报告的大小不超过 1024，直接调用它的是信号帧与 `ptrace` 的代码（`os/StarryOS/signal/src/arch/x86_64.rs`、`syscall/task/ptrace.rs`），启动路径不调用。第 216 行的文档链接仍指向 `platforms/someboot/src/arch/x86_64/trap.rs`，`enable_xsave_features` 实际已搬到 `components/axcpu/src/arch/x86_64/boot.rs` 第 98 行。

## 溯源复核

- PR 正文称「任何重度使用 AVX 的程序（例如 JVM）都会因此在用户态读到被破坏的 YMM 值，进而 SIGSEGV 崩溃」。YMM 高 128 位被覆盖这一点有回归用例为证；把 JVM 的崩溃归到这里则没有证据。本地记录（`notes/91-comprehensive-state-0619.md`）写明：2026-06-21 确认本补丁已编进 x86_64 内核，Java 用例仍然 SIGSEGV。此后的本地记录把那次失败先后归到 [#1331](pr-1331.md)（同步 `SIGSEGV` 没有填 `si_addr`）、[#1366](pr-1366.md)（新任务的 x87 标记字）与 [#1367](pr-1367.md)（`#DE` 没有按 `SIGFPE` 投递），都与 YMM 的上下文切换无关。
- 补丁没有检查 XSAVE 区的实际大小，见上文「与 Linux 的差异」第一条。合入时启动路径只开三个分量，832 字节在 1024 之内，当时不会越界。

## 验证

- `test-x86-avx-ctxsw`：主线程把一个已知值装进 `ymm15`，在同一段内联汇编里用原始 `syscall` 指令连续执行 20000 次 `sched_yield`，再读回；同时有 4 个线程不停地把各自的值写满 `ymm0` 至 `ymm15` 并让出 CPU。分别断言低 128 位与高 128 位未变。CPU 不带 XSAVE 或 AVX 时跳过，非 x86_64 架构跳过。
- PR 正文：只用 FXSAVE 的基线上低 128 位完好、高 128 位读回别的线程的值（`expected cafebabedeadbeef 0123456789abcdef, got 2d88b3b0a87ca501 1ebb80839b4f9632`），用例失败；补丁之后 4/4 断言通过。
- 评审记录（ZR233）：本地执行 `cargo xtask clippy --package ax-cpu` 与 `cargo xtask starry test qemu --arch x86_64 -c qemu-smp1/test-x86-avx-ctxsw` 通过。CI 上格式、clippy、StarryOS x86_64 QEMU 等检查通过；`Test axvisor self-hosted x86_64 / run_host` 的 `smoke-vmx` 超时，评审按既有的 #1230 归类，未作为阻塞项。
- 当前 dev 上用例仍在，位置是 `test-suit/starryos/qemu/system/test-x86-avx-ctxsw`；该组的 `qemu-x86_64.toml` 仍用 `-cpu Haswell,+avx`。
