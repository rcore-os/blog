## 问题与原因

`ExtendedState::default()` 给新任务的 FXSAVE 区写 `ftw = 0xffff`。FXSAVE 格式的标记字是缩略形式：低字节每一位对应一个 x87 寄存器，1 表示有内容，0 表示空。`0xffff` 是旧的 FSAVE 格式（每个寄存器 2 位，`11` 为空）里「全空」的写法，写进 FXSAVE 区后低字节是 `0xff`，八个寄存器全被标成有内容，x87 栈是满的。

受影响的是用 FXRSTOR 恢复的路径，即没有 XSAVE 的 CPU 型号（默认的 `qemu64`）：新任务第一次被换入时装入这份状态，第一条 `fld` 就栈上溢，得到 x87 的不定值。带 XSAVE 的型号上，[#1329](pr-1329.md) 之后新任务由 `XRSTOR` 按全零的 `XSTATE_BV` 初始化 x87，不读这个字段，不受影响。这个初值在 #1329 之前就有（#1329 的 diff 原样保留了它），那时所有型号都用 FXRSTOR 恢复。

合入时每个新任务的 `TaskContext` 都以 `ExtendedState::default()` 起步，所以在受影响的型号上，任何在新进程或新线程里使用 x87 的代码都会撞上；x86_64 的 `long double` 运算走 x87。

## 改动与影响范围

`default()` 里的 `area.legacy.ftw = 0xffff` 改为 `0x0000`，并加一段注释说明两种标记字格式的区别。`fcw = 0x37f` 与 `mxcsr = 0x1f80` 不变。

影响范围：x86_64 上 FXRSTOR 回退路径中所有新建任务的初始 x87 状态。XSAVE 路径的行为不变。不涉及系统调用。

与 Linux 的差异：

- 补丁之后，初始映像的三个字段与 Linux 的 FXSAVE 初始映像一致（`cwd = 0x37f`、`mxcsr = 0x1f80`、标记字为 0）。
- 状态的来源不同。Linux 的 `clone` 子任务继承父任务当时的 FPU 状态，`execve` 才回到初始映像；合入时的 StarryOS 给每个新任务一份 `default()`，补丁改的是这份默认值，没有改继承关系。

当前 dev：这一行在 `components/axcpu/src/arch/x86_64/context.rs` 第 581 行，注释保留（第 565 至 580 行）。FPU 状态的来源已经向 Linux 靠拢：`clone`（`os/StarryOS/kernel/src/syscall/task/clone.rs` 第 526 行的 `inherit_current_fp()`）经 `context.rs` 第 731 行的 `clone_user_fp_state_into` 继承父任务的状态；`execve`（`os/StarryOS/kernel/src/syscall/task/execve.rs` 第 441 行）经 `context.rs` 第 784 行的 `reset_user_fp_state` 回到 `default()`。

## 溯源复核

- 回归用例在 CI 上拦不住这个缺陷。系统测试组的 `qemu-x86_64.toml` 用 `-cpu Haswell,+avx`，走 XSAVE 路径，用例在修复前后都通过；PR 正文已说明这一点。正文与评审记录里也没有该用例在 `qemu64` 上修复前失败的运行结果，用例头部注释写的「修复前 FAIL」没有运行记录对应。当前 dev 的系统测试组仍用 `Haswell,+avx`。
- PR 正文的因果链（满栈使 `fld` 溢出得到不定值，musl 的 `fmt_fp` 因此越界改写 `%fs:0`，引出 `0x34` 处的递归 `SIGSEGV`）没有附调试记录。给出的证据是端到端的前后对照：`qemu64` 型号上 Java 用例修复前无法运行，修复后通过。本地当晚的排查笔记（`notes/97-x86-java-tls-storm-debugging.md`）记的是另一种机制：线程栈与 TLS 所在的页被另一线程 `munmap` 后复用清零；那条线上的修改没有提交。`memory/project_x86_java_checkpoint_0624.md`（24.04）记的最终结论是本补丁。中间环节待核实。
- 评审指出用例初版在工作线程里先执行了 `fninit`，会把标记字清空，旧的初值也能通过。作者删掉后强推（`60c587f2a`），合入的版本里 `fninit` 只出现在读状态字之后。
