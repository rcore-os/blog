## 问题与原因

`test-open-family` 套件对照 Linux 揭出 `open`/`openat` 的一批偏差，本拉取请求修其中只需局部改动的 15 类，按成因分四组：

1. O_PATH 语义不全：`O_PATH` 在 `flags_to_options` 里只是众多标志之一，后面的 `O_CREAT`、`O_EXCL`、`O_TRUNC`、写访问仍然生效；`fstat` 取 O_PATH 描述符的后端时直接报 `EBADF`。
2. 入口参数检查缺失：超长路径、空路径、`O_CREAT|O_DIRECTORY`、只读的 `O_TMPFILE` 都没有被拒绝；绝对路径仍去解析 `dirfd`，`dirfd` 无效时误报 `EBADF`。
3. 目录与符号链接：`O_CREAT` 打开已存在的目录不报 `EISDIR`；`O_NOFOLLOW` 遇到末级符号链接不报 `ELOOP`。
4. 访问模式真值表：`O_RDONLY|O_APPEND` 被悄悄升级成读写；`O_RDONLY|O_TRUNC`、`O_RDWR|O_APPEND|O_TRUNC` 被 `is_valid()` 拒绝；`O_APPEND` 打开时把文件位置设到文件尾。

## 改动与影响范围

| 修改点 | 位置 | 内容 | 对应 Linux 行为 |
|:--:|:--:|:--:|:--:|
| `resolve_at` | `file/fs.rs` | 取 `location()` 而不取 `backend()`，O_PATH 描述符可作 `fstat` 与 `*at` 的起点 | `vfs_fstat` 用 `fd_raw`，接受 O_PATH |
| `flags_to_options` | `syscall/fs/fd_ops.rs` | `O_PATH` 放到最后覆盖：只读、清掉创建、独占、截断、追加 | `build_open_how` 中「O_PATH beats everything else」 |
| `sys_openat` 五项检查 | `syscall/fs/fd_ops.rs` | 长度不小于 4096 报 `ENAMETOOLONG`；空路径 `ENOENT`；`O_CREAT|O_DIRECTORY` 与只读 `O_TMPFILE` 报 `EINVAL`（O_PATH 例外）；绝对路径忽略 `dirfd` | `getname_flags`、`build_open_flags`、`path_init` |
| `OpenOptions::_open` | `axfs-ng/highlevel/file.rs` | `O_CREAT` 命中已有目录报 `EISDIR` | `do_open` |
| `OpenOptions::open` | 同上 | 空路径 `ENOENT`（两层都查）；`O_NOFOLLOW` 且末级为符号链接报 `ELOOP` | `may_open` |
| `to_flags` / `is_valid` | 同上 | 访问模式与追加位分开；只要有读、写、追加之一即合法 | 访问模式只由低两位决定，`O_TRUNC` 与只读可共存 |
| `File::new` / `File::write` | 同上 | 打开时位置恒为 0；写入先检查写权限位 | `vfs_write` 无 `FMODE_WRITE` 报 `EBADF`，追加在每次写时定位 |

影响范围：所有经 `open`/`openat`/`creat` 进入的路径，以及 `axfs-ng` 的 `OpenOptions`（ArceOS 侧的文件打开共用这段代码）。`O_RDONLY|O_APPEND` 描述符此前可写，修复后写入返回 `EBADF`，依赖旧行为的程序会看到错误，这与 Linux 一致。

## 代码对照

### `O_PATH` 覆盖其余标志

合入前（`os/StarryOS/kernel/src/syscall/fs/fd_ops.rs` 的 `flags_to_options`，`O_PATH` 与其余标志并列，各自生效）：

```rust
if flags & O_CREAT != 0 {
    options.create(true);
}
if flags & O_PATH != 0 {
    options.path(true);
}
```

Linux（[fs/open.c#L1170-L1172](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/fs/open.c#L1170-L1172)，`build_open_how()`；`O_PATH_FLAGS` 是 `O_DIRECTORY | O_NOFOLLOW | O_PATH | O_CLOEXEC`）：

```c
	/* O_PATH beats everything else. */
	if (how.flags & O_PATH)
		how.flags &= O_PATH_FLAGS;
```

本 PR（同一函数的末尾，当前 dev 上仍是这段）：

```rust
if flags & O_PATH != 0 {
    options.path(true);
    // O_PATH: drop access mode (no I/O), drop create/excl/trunc/append
    options.read(true).write(false);
    options
        .create(false)
        .create_new(false)
        .truncate(false)
        .append(false);
}
options
```

### 入口的标志组合检查

合入前 `sys_openat` 读出路径后直接计算 `mode` 并进入打开流程，没有这两项检查。

Linux（[fs/open.c#L1224-L1238](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/fs/open.c#L1224-L1238)，`build_open_flags()`）：

```c
	if ((flags & (O_DIRECTORY | O_CREAT)) == (O_DIRECTORY | O_CREAT))
		return -EINVAL;

	/* Now handle the creative implementation of O_TMPFILE. */
	if (flags & __O_TMPFILE) {
		/*
		 * In order to ensure programs get explicit errors when trying
		 * to use O_TMPFILE on old kernels we enforce that O_DIRECTORY
		 * is raised alongside __O_TMPFILE.
		 */
		if (!(flags & O_DIRECTORY))
			return -EINVAL;
		if (!(acc_mode & MAY_WRITE))
			return -EINVAL;
	}
```

本 PR（`os/StarryOS/kernel/src/syscall/fs/fd_ops.rs` 的 `sys_openat`，当前 dev 上两项判断仍在）：

```rust
let uflags = flags as u32;
// ...
if uflags & O_CREAT != 0 && uflags & O_DIRECTORY != 0 && uflags & O_PATH == 0 {
    return Err(AxError::InvalidInput);
}
// ...
if uflags & O_TMPFILE == O_TMPFILE && uflags & 0b11 == O_RDONLY && uflags & O_PATH == 0 {
    return Err(AxError::InvalidInput);
}
```

### 访问模式与追加位

合入前（`os/arceos/modules/axfs-ng/src/highlevel/file.rs` 的 `to_flags`，带追加位就补上写权限）：

```rust
Ok(match (self.read, self.write, self.append) {
    (true, false, false) => FileFlags::READ,
    (false, true, false) => FileFlags::WRITE,
    (true, true, false) => FileFlags::READ | FileFlags::WRITE,
    (false, _, true) => FileFlags::WRITE | FileFlags::APPEND,
    (true, _, true) => FileFlags::READ | FileFlags::WRITE | FileFlags::APPEND,
    (false, false, false) => return Err(VfsError::InvalidInput),
```

Linux（[fs/read_write.c#L668-L673](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/fs/read_write.c#L668-L673)，写入只看 `FMODE_WRITE`）：

```c
ssize_t vfs_write(struct file *file, const char __user *buf, size_t count, loff_t *pos)
{
	ssize_t ret;

	if (!(file->f_mode & FMODE_WRITE))
		return -EBADF;
```

本 PR（同一文件，后半段在写入路径的开头；当前 dev 上 `to_flags` 搬到 `fs/ax-fs-ng/src/file/open.rs`，分支与这里相同）：

```rust
Ok(match (self.read, self.write, self.append) {
    (true, false, false) => FileFlags::READ,
    (false, true, false) => FileFlags::WRITE,
    (true, true, false) => FileFlags::READ | FileFlags::WRITE,
    (true, false, true) => FileFlags::READ | FileFlags::APPEND,
    (false, true, true) => FileFlags::WRITE | FileFlags::APPEND,
    (true, true, true) => FileFlags::READ | FileFlags::WRITE | FileFlags::APPEND,
    (false, false, true) => FileFlags::APPEND, // RDONLY-equivalent + APPEND: pure status
    (false, false, false) => return Err(VfsError::InvalidInput),
// ...
// WRITE bit is mandatory for any write path, regardless of whether
// APPEND is set. Otherwise O_RDONLY|O_APPEND fd would silently
// succeed writes (since access(APPEND) only checks the APPEND bit).
// Fixes bug-open-rdonly-append-promotes-rw (the part inside axfs).
self.access(FileFlags::WRITE)?;
```

## man 原文

均摘自 [open(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/open.2?h=man-pages-6.19)，行号为源文件行号。

- [open(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/open.2?h=man-pages-6.19#n83)：The file offset is set to the beginning of the file (see lseek(2)).
- [open(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/open.2?h=man-pages-6.19#n150)：O_APPEND The file is opened in append mode. Before each write(2), the file offset is positioned at the end of the file, as if with lseek(2).
- [open(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/open.2?h=man-pages-6.19#n521)：O_NOFOLLOW If the trailing component (i.e., basename) of path is a symbolic link, then the open fails, with the error ELOOP.
- [open(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/open.2?h=man-pages-6.19#n596)：The file itself is not opened, and other file operations (e.g., read(2), write(2), fchmod(2), fchown(2), fgetxattr(2), ioctl(2), mmap(2)) fail with the error EBADF. The following operations can be performed on the resulting file descriptor: … fstat(2) (since Linux 3.6).
- [open(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/open.2?h=man-pages-6.19#n665)：When O_PATH is specified in flags, flag bits other than O_CLOEXEC, O_DIRECTORY, and O_NOFOLLOW are ignored.
- [open(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/open.2?h=man-pages-6.19#n909)：If the pathname given in path is absolute, then dirfd is ignored.
- [open(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/open.2?h=man-pages-6.19#n1070)：EINVAL O_TMPFILE was specified in flags, but neither O_WRONLY nor O_RDWR was specified.
- [open(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/open.2?h=man-pages-6.19#n1080)：EINVAL O_CREAT and O_DIRECTORY were both specified in flags, and the Linux kernel version is 6.4 or later.
- [open(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/open.2?h=man-pages-6.19#n1105)：EISDIR path refers to a directory and the access requested involved writing (that is, O_WRONLY or O_RDWR is set).
- [open(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/open.2?h=man-pages-6.19#n1132)：ELOOP path was a symbolic link, and flags specified O_NOFOLLOW but not O_PATH.
- [open(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/open.2?h=man-pages-6.19#n1148)：ENAMETOOLONG path was too long.
- [open(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/open.2?h=man-pages-6.19#n1297)：The (undefined) effect of O_RDONLY | O_TRUNC varies among implementations. On many systems the file is actually truncated.

`EISDIR` 条目只写了写访问，`O_CREAT|O_RDONLY` 命中目录同样报 `EISDIR` 来自 `do_open` 的实现（上节链接），man 没有单列。
