## 问题与原因

`RLIMIT_AS` 在 StarryOS 上既没有默认值也没有人检查。`Rlimits::default()` 只给栈、描述符数、数据段等几项赋值，其余项是 `Rlimit` 的零值，所以 `getrlimit(RLIMIT_AS)` 读到软硬上限都是 0；同时内核里没有任何一处读这个限额，`setrlimit(RLIMIT_AS)` 之后 `mmap`、`mremap`、`brk`、`shmat` 照常成功。靠这个限额约束自身内存的程序（浏览器的沙箱进程、按限额估算可用地址空间的运行时）得不到 `ENOMEM`。当前 dev 仍是这个状态：`git grep RLIMIT_AS` 在内核源码里没有命中。

## 改动与影响范围

| 修改点 | 位置 | 内容 |
|:--:|:--:|:--:|
| 默认值 | `task/resources.rs` | `RLIMIT_AS` 软硬上限都设为无穷，与 `INIT_RLIMITS` 一致 |
| 判定 | `mmap.rs` 的 `exceeds_rlimit_as()`、`check_rlimit_as()` | 「已映射页数 − 本次要替换掉的页数 + 本次新增页数」超过「限额字节数 ÷ 页大小」即 `ENOMEM`；限额为无穷时不查 |
| `mmap` | `sys_mmap` 的 `admit_mapping()` | 先定址；`MAP_FIXED_NOREPLACE` 的目标已有映射返回 `EEXIST`；`MAP_FIXED` 覆盖已有映射时把被替换的页数扣掉再比；这一步在设备的 `device_mmap` 回调之前 |
| `mremap` | `sys_mremap` 的四条路径 | 原地扩大按增量计；搬移按新长度与旧长度之差计；`MREMAP_DONTUNMAP` 按整段新长度计；`MREMAP_FIXED` 扣掉目标处被替换的页 |
| `brk` | `sys_brk` | 只计超出装载时堆区的增长；超限时返回原 break，不报错 |
| `shmat` | `sys_shmat` | 整段附着长度计入 |
| `execve` | `do_execve`、`exec_strings_exceed_rlimit_as()`、`force_fatal_sig()` | 分两段。装载之前：文件名、参数与环境字符串在新栈里占的页数多于一页且超过限额，返回 `E2BIG`。新地址空间建好之后：总大小超过限额，以 `SIGSEGV` 终止调用者，不管进程装了什么处理函数 |

影响范围：`mmap`、`mremap`、`brk`、`shmat`、`execve`、`execveat` 六个系统调用，以及 `getrlimit`/`prlimit64` 读到的 `RLIMIT_AS` 默认值。限额保持默认（无穷）的进程行为不变。

与 Linux 的差异：

- Linux 的栈按需增长，每次增长由 `acct_stack_growth()` 计费。StarryOS 的装载器一次映射整个 8 MiB 用户栈与 64 KiB 初始堆，这部分在 `execve` 时就计入。限额低于「映像加 8 MiB 栈」时，StarryOS 在 `execve` 就终止进程，Linux 要到栈实际长到限额才终止。
- Linux 在 `may_expand_vm()` 里同时检查 `RLIMIT_DATA`（对可写私有映射），本补丁不动 `RLIMIT_DATA`，`brk` 原有的 `RLIMIT_DATA` 检查保留。
- 已用量取 `aspace.vm_stat.vss_pages()`，对应 Linux 的 `mm->total_vm`；两者的口径是否逐项相同（例如设备映射、保护页）没有逐一核对，待核实。

评审经过五轮，都是同一类问题：检查点的覆盖面与先后次序。

| 轮次 | 意见 | 处理 |
|:--:|:--:|:--:|
| 09.15 | `MAP_FIXED_NOREPLACE` 的冲突应先于限额返回 `EEXIST` | 冲突预检前移 |
| 09.25 | `brk` 与 `shmat` 不受限 | 两处接入同一检查 |

| 10.04 | `execve` 装载新映像不计费，可以借 exec 越过限额 | `execve` 按 Linux 的两段计费 |

## 溯源复核

- 10.02 这一轮暴露的问题是真实的：perf 采样事件的 `device_mmap` 会把环形缓冲交给采样线程，随后被限额拒绝时 VMA 没装上而事件状态已变，同一个描述符再映射得到 `EBUSY`。aarch64 上把事件改成打开即启用后，旧实现 53 过 1 挂，可以复现。
- 回归用例第一版以禁用态打开事件，采样输出要到启用后才登记，所以「放开限额后重试」那一项在旧实现上并不失败；这一项是后来才具备判别力的。
- perf 环形缓冲的三项只在 aarch64 上执行，x86_64 与 riscv64 上内核不映射采样环，用例跳过并打印原因。这三项在这两个架构上没有覆盖。
- ION 映射分支只存在于 SG2002 板上，QEMU 构造不出来，只有编译覆盖。
- 10.04 这一轮的评审意见说 Linux 上超限的 `execve`「返回 `ENOMEM`、原映像继续运行」，这与源码不符。映像各段在 `begin_new_exec()` 之后才映射，那时已经没有可以返回的原映像，`bprm_execve()` 以 `SIGSEGV` 终止调用者；能让调用失败并保留原映像的只有装载之前的参数页，错误码是 `E2BIG`。宿主 Linux 6.6 实测与源码一致：限额一页时，两页参数得到 `E2BIG`，参数放得下则子进程被信号 11 终止。补丁按源码实现，没有照评审意见做。

## man 原文

[getrlimit(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/getrlimit.2?h=man-pages-6.19#n77)：

> RLIMIT_AS This is the maximum size of the process's virtual memory (address space). The limit is specified in bytes, and is rounded down to the system page size. This limit affects calls to brk(2), mmap(2), and mremap(2), which fail with the error ENOMEM upon exceeding this limit. In addition, automatic stack expansion fails (and generates a SIGSEGV that kills the process if no alternate stack has been made available via sigaltstack(2)).

[mmap(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/mmap.2?h=man-pages-6.19#n522)：

> EEXIST MAP_FIXED_NOREPLACE was specified in flags, and the range covered by addr and length clashes with an existing mapping.

man 页没有把 `shmat` 列进受 `RLIMIT_AS` 影响的调用；它受限是 Linux 实现经 `do_mmap()` 带来的结果。
