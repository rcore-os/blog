## 问题与原因

QEMU 以 `-smp M` 启动、内核按 `MAX_CPU_NUM == N`（`N < M`）编译时，第 N 到 M-1 个核进入 `rust_main_secondary` 后立即用 `cpu_id` 去索引按 `MAX_CPU_NUM` 定长的每核结构（`percpu::init_secondary`、`AxCpuMask::one_shot`、`RUN_QUEUES`），越界断言导致内核恐慌、启动失败。本地记录里的实际触发场景是 riscv64 测试配置写了 `-smp 4`，而该架构的内核按单核编译。

## 改动与影响范围

`rust_main_secondary` 在 `init_secondary` 之前判断 `cpu_id >= MAX_CPU_NUM`，是则进入 `wait_for_irqs()` 死循环，永久停住，不触碰任何每核结构。`cpu_id < MAX_CPU_NUM` 的核行为不变。

影响范围：只有编号超出编译期上限的次级核；这些核不参与调度，系统按前 N 个核运行。

当前 dev：启动代码已重写，`rust_main_secondary` 改用 `secondary_cpu_is_usable(cpu_id, ax_hal::cpu_num())` 判断（`cpu_num()` 已取平台核数与编译上限的较小值），思路相同。

    }

## Linux 依据

Linux 同样只使用前 `NR_CPUS` 个处理器，超出的在枚举阶段直接跳过，不会被拉起：

- riscv 设备树枚举：`cpuid >= NR_CPUS` 时告警并跳过该 hart：[arch/riscv/kernel/smpboot.c#L142-L146](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/arch/riscv/kernel/smpboot.c#L142-L146)
- 区别：Linux 在拉起之前就不启动多余的核，这些核停在固件里；StarryOS 这里多余的核已经进入内核入口，只能就地停住。
