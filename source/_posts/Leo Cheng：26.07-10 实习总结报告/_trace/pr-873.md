## 问题与原因

ArceOS 的 `task/ipi` 多核测试在 loongarch64（QEMU `-smp 4 -cpu la464`）上偶发挂起约 6 小时，被持续集成超时取消，拖住了与多核无关的拉取请求（例如 #730）。拉取请求当时的判断是：`send_ipi` 写 `IOCSR_IPI_SEND` 时带了阻塞位（第 31 位），发送方会一直等到目标核清掉 `IOCSR_IPI_STATUS`，高频突发下双方都关着中断，互相等待。

## 改动与影响范围

`send_ipi` 的三种目标（本核、指定核、除本核外全部）把 `make_ipi_send_value(.., true)` 改成 `false`，即写入值去掉第 31 位，其余位（目标核号在 16–25 位，向量在 0–4 位）不变。影响范围只有 loongarch64 QEMU 平台的运行时核间中断，启动期邮箱不受影响。

## 代码对照

### `send_ipi` 的阻塞位

合入前（`components/axplat_crates/platforms/axplat-loongarch64-qemu-virt/src/irq.rs`，第三个参数为 `true`，写入值带第 31 位）：

```rust
fn send_ipi(_irq_num: usize, target: IpiTarget) {
    match target {
        IpiTarget::Current { cpu_id } => {
            iocsr_write_w(IOCSR_IPI_SEND, make_ipi_send_value(cpu_id, 0, true));
        }
        IpiTarget::Other { cpu_id } => {
            iocsr_write_w(IOCSR_IPI_SEND, make_ipi_send_value(cpu_id, 0, true));
        }
```

Linux（[arch/loongarch/kernel/smp.c#L226-L233](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/arch/loongarch/kernel/smp.c#L226-L233)）：

```c
static void ipi_write_action(int cpu, u32 action)
{
	uint32_t val;

	val = IOCSR_IPI_SEND_BLOCKING | action;
	val |= (cpu << IOCSR_IPI_SEND_CPU_SHIFT);
	iocsr_write32(val, LOONGARCH_IOCSR_IPI_SEND);
}
```

本 PR（同一文件，三种目标都改成 `false`）：

```rust
fn send_ipi(_irq_num: usize, target: IpiTarget) {
    match target {
        IpiTarget::Current { cpu_id } => {
            iocsr_write_w(IOCSR_IPI_SEND, make_ipi_send_value(cpu_id, 0, false));
        }
        IpiTarget::Other { cpu_id } => {
            iocsr_write_w(IOCSR_IPI_SEND, make_ipi_send_value(cpu_id, 0, false));
        }
```

当前 dev（`platforms/somehal/src/arch/loongarch64/ipi_command.rs`，原平台包已移除，#1916 与 #1775 重写后写入值重新带阻塞位）：

```rust
pub(crate) const IOCSR_IPI_SEND_CPU_SHIFT: u32 = 16;
pub(crate) const IOCSR_IPI_SEND_BLOCKING: u32 = 1 << 31;
// ...
pub(crate) fn make_ipi_send_value(cpu_id: usize, vector: u32) -> Option<u32> {
    if cpu_id > MAX_CPU_ID || vector > MAX_VECTOR {
        return None;
    }
    Some(IOCSR_IPI_SEND_BLOCKING | ((cpu_id as u32) << IOCSR_IPI_SEND_CPU_SHIFT) | vector)
}
```

## 溯源复核（2026-09-29）

复核结论：**这个修改在 QEMU 上没有功能差别，正文给出的根因不成立**，由以下三点可证：

1. QEMU 10.2.1 处理 `IOCSR_IPI_SEND` 时只取目标核号与向量，直接置位目标核的状态寄存器，从不读第 31 位：[hw/intc/loongson_ipi_common.c#L179-L188](https://gitlab.com/qemu-project/qemu/-/blob/v10.2.1/hw/intc/loongson_ipi_common.c#L179-L188)。去掉阻塞位后写入 QEMU 的效果完全相同。
2. 阻塞位的含义也不是「等目标核清状态」。Linux 在 LoongArch 上发送所有运行时核间中断都带这一位：[arch/loongarch/kernel/smp.c#L226-L233](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/arch/loongarch/kernel/smp.c#L226-L233)，常量定义 [arch/loongarch/include/asm/loongarch.h#L1211-L1214](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/arch/loongarch/include/asm/loongarch.h#L1211-L1214)。代码注释里「Linux/riscv/x86 likewise fire runtime IPIs non-blocking」对 LoongArch 上的 Linux 不成立。硬件手册对第 31 位的确切表述本次没有找到可链接的一手来源，待核实。
3. 本地记录 `notes/33` 写明：#730 推空提交重新触发时「恰好撞上一次没死锁」就全绿了。挂起本来就是偶发的，修复后的单次通过不能证明修复有效。

后续：该平台包已随上游重构移除，现在的 LoongArch 核间中断在 `platforms/somehal/src/arch/loongarch64/`，由 #1916（2026-08-07）与 #1775（2026-09-08）重写，写入值重新带上 `IOCSR_IPI_SEND_BLOCKING`，与 Linux 一致。本拉取请求的改动已不在当前代码中。挂起的真正原因没有定位。
