## 问题与原因

内核里的随机数没有一个可信的来源，三处各管各的：

- `AT_RANDOM` 是常量。当前 dev 的 `mm/loader.rs` 仍把 `b"0123456789abcdef"` 压进用户栈。libc 用这 16 字节生成栈保护金丝雀与指针保护值，常量意味着两者可被推算。
- `/dev/random` 与 `/dev/urandom` 各自持有一个 ChaCha20，种子取自单调时钟、计数器与栈地址；riscv64 与 loongarch64 上没有任何不可预测的输入。
- `/proc/sys/kernel/random/boot_id` 直接取引导种子的前 16 字节，等于把引导熵公开出去。

平台其实已经提供了可信的引导熵接口 `boot_entropy()`（UEFI RNG 或 FDT 的 `/chosen/rng-seed`），只是没有消费者按「已由不可预测的熵播种」这个条件来使用它。

## 改动与影响范围

新增模块 `kernel/src/random`，按 Linux `drivers/char/random.c` 的就绪契约转写：

| 修改点 | 位置 | 内容 |
|:--:|:--:|:--:|
| 输入池与就绪条件 | `random/mod.rs` | 池累计「计入的熵位数」，达到 256 位才就绪。计入三类输入：引导种子按字节数乘 8；CPU 随机指令每个 64 位字计 64 位；时钟抖动每若干样本计 1 位。启动时间戳与用户写入只混入、不计入 |
| CPU 随机指令 | `random/arch.rs` | x86_64 用 RDSEED/RDRAND，aarch64 用 RNDR，riscv64 与 loongarch64 没有；特性位在所有在线 CPU 上都具备才算可用 |
| 抖动收集 | `random/mod.rs` | 先读 8192 次时钟估出每位需要的样本数，时钟太粗就不收集；否则循环取样到就绪或有待处理信号 |
| 取数 | `random/mod.rs` 的 `Crng` | 32 字节密钥驱动 ChaCha20，每次取数先用输出替换密钥，就绪后按间隔重新播种；流的状态与各处栈上副本用后清零 |
| `getrandom` | `syscall/sys.rs` | 不再经 VFS 打开设备，直接取 CRNG；先查标志再看长度；未就绪时 `GRND_NONBLOCK` 返回 `EAGAIN`，否则等待且可被信号打断；写用户内存遇缺页返回已写入的字节数 |
| `/dev/random`、`/dev/urandom` | `pseudofs/dev/mod.rs` | 两个设备都改为取同一个 CRNG；前者未就绪时不可读、`poll` 报可写，后者不等待、未就绪时限频打印提示 |
| 阻塞读的等待 | `pseudofs/device.rs` 的 `DeviceOps::wait_readable`；`file/fs.rs`；`syscall/fs/io.rs` | 设备可以在阻塞读之前先做自己的等待。`read`、`pread64`、`preadv2` 三条路径都经过；`O_NONBLOCK` 的读者跳过。`/dev/random` 的等待就是 `wait_for_random_bytes()`，与阻塞的 `getrandom` 同一条路径 |
| ioctl | `random/mod.rs` 的 `random_ioctl()` | 两个设备共用：`RNDGETENTCNT`、`RNDADDTOENTCNT`、`RNDADDENTROPY`、`RNDZAPENTCNT`、`RNDCLEARPOOL`、`RNDRESEEDCRNG`，其他命令返回 `EINVAL` |
| `AT_RANDOM` 等 | `mm/loader.rs` | `AT_RANDOM` 由 `get_random_bytes()` 填；补 `AT_CLKTCK=100`、`AT_FLAGS=0` |
| `boot_id` | `pseudofs/proc.rs` | 改从 CRNG 生成；CRNG 未就绪时不创建这个文件 |

影响范围：`getrandom`、两个随机设备的读、`poll` 与 `ioctl`、每次 `execve` 的辅助向量、`boot_id`。各平台的熵来源：x86_64 是 UEFI RNG 加 RDRAND/RDSEED；riscv64 与 aarch64 是 QEMU virt 下发的 `/chosen/rng-seed`；loongarch64 以 UEFI 启动时两者都没有，由第一个阻塞的 `getrandom()` 调用者收集抖动后就绪。

与 Linux 的差异（PR 正文已列）：

- 池的哈希 Linux 用 BLAKE2s，这里用工作区已有的 SHA-256。
- Linux 的抖动样本由定时器回调取，这里在收集循环里检测节拍边界。
- 没有做每 CPU 的 CRNG。

评审经过：

| 轮次 | 意见 | 处理 |
|:--:|:--:|:--:|
| 09.15 | `/dev/urandom` 读不应收集熵；`AT_RANDOM` 必须等可信熵 | 两条都对照 Linux 源码回绝：`urandom_read_iter()` 未就绪时同样调用 `try_to_generate_entropy()`；`create_elf_tables()` 用不等待的 `get_random_bytes()` |
| 09.28 | 随机指令的可用性由第一个探测的 CPU 决定，异构 CPU 上可能在不支持的核上执行 | 采纳，改为所有在线 CPU 取交集 |
| 10.02 | `ChaCha20Rng` 没有 `Drop` 与 `Zeroize`，旧密钥留在流状态与栈上 | 采纳，打开 `zeroize` 特性，各处副本用后清零 |
| 10.04 | `/dev/random` 的阻塞读只挂在等待队列上、不收集抖动，没有熵源的平台上不返回；`pread` 在阻塞描述符上得到 `EAGAIN` | 采纳，阻塞读先走 `wait_for_random_bytes()`；顺带补上 ioctl |

## 溯源复核

- PR 正文写对照的是 v7.2-rc3；本文的行号一律取自固定版本 7.1.0（提交 `8cd9520d`），所列函数在该版本里逐一查到。
- 09.15 的两条意见与 Linux 源码不符，回绝是有依据的，见下节 `urandom_read_iter()` 与 `create_elf_tables()` 两条。
- 10.02 的擦除回归是一条编译期断言（两种流类型都实现 `ZeroizeOnDrop`），它能防止特性被关掉，但不检查内存里是否真的没有残留。
- 10.04 这一轮的问题是真实的，而且此前写在「与 Linux 的差异」里当作已知限制。loongarch64 以 UEFI 启动时没有引导熵也没有随机指令，把阻塞的 `read` 放到用例最前面，旧内核上 120 秒超时；其余三个架构启动时已经就绪，暴露不出来。原先的理由「设备读接口拿不到调用任务」不成立，加一个钩子即可。
- loongarch64 上只有抖动这一种熵。`try_to_generate_entropy()` 在 Linux 里同样被当作熵源，但它依赖时钟读数的不可预测性；QEMU 下这一点的强度没有度量。

## 验证

数字取自 PR 正文。

- 宿主单测 `random::tests` 直接验证就绪契约：只混入时间与写入时保持未就绪；31 字节引导种子不够、32 字节就绪；3 个 CPU 字不够、4 个就绪；时钟不变时不收集抖动；每次取数后密钥改变；重新播种间隔；提示限频；随机指令在任一 CPU 上缺失即视为不可用；流类型实现 `ZeroizeOnDrop`。
- `syscall-test-getrandom`：阻塞调用返回完整长度；非法标志与 `GRND_INSECURE|GRND_RANDOM` 返回 `EINVAL`；先查标志再看长度；`EFAULT`；跨越不可写页时只返回边界前的字节数；两个设备的设备号与 `poll` 结果。10.04 起阻塞的 `read` 与 `pread` 放在最前面，并对两个设备各测一遍 ioctl（就绪后 `RNDGETENTCNT` 读到 256、坏指针 `EFAULT`、负的熵位数 `EINVAL`、数据跨到不可读的页 `EFAULT`、没有 `CAP_SYS_ADMIN` 时除 `RNDGETENTCNT` 外都是 `EPERM`）。宿主 Linux 6.6 上以 root 运行 66 项全过。
- `test-auxv`：`AT_CLKTCK`、`AT_FLAGS`，两次重新 `exec` 得到的 `AT_RANDOM` 互不相同。宿主 Linux 6.6 上 31 项全过。
- 修复前（dev 加用例，x86_64）：`syscall-test-getrandom` 3 项失败，`test-auxv` 6 项失败。把时间戳计入熵的变体上，单测 `uncredited_input_leaves_the_crng_unready` 失败。未收集抖动的前一版在 loongarch64 上阻塞 120 秒超时。
- 修复后：x86_64、riscv64、aarch64 两个用例各 31 项全过；loongarch64 通过，阻塞调用收集抖动后 2.7 秒内返回。
- 最近一轮（10.02）：x86_64 与 aarch64 两个用例各 31 项全过，`qemu/system` 分组 524 个用例程序全过，`ktest` 207 项全过，`clippy --package starry-kernel` 80 项检查通过；旧的 `random/mod.rs` 加擦除单测时编译失败。
- 10.04 一轮：loongarch64 上只加用例时第一个阻塞读不返回，120 秒超时，修复后 2.7 秒通过；x86_64 上只加用例时 40 过 26 挂（ioctl 全部返回 `ENOTTY`），修复后 66 项全过；aarch64 与 riscv64 各 66 项全过；`qemu/system` 分组 524 个用例程序全过；`ktest` 207 项全过；`clippy --package starry-kernel` 80 项检查通过。
