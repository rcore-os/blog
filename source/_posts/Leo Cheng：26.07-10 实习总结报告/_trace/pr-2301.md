## 问题与原因

slab 的每个 size class 有 partial、full、empty 三条链表。别的 CPU 释放对象时不取属主的锁，只把对象挂到 slab 页头的远程释放队列上；属主 CPU 要在分配时自己发现。`SlabCache::alloc_object` 的做法是：partial 链表取不到对象时，遍历整条 full 链表，逐个页头看有没有远程释放。

跨 CPU 释放很少，这次遍历几乎总是一无所获，代价随 full slab 的数量线性增长。PR 的用例量到：512 次分配遍历了 2701 个节点。浏览器负载下对内核采样，`reclaim_full_with_remote_frees` 是出现最多的栈顶符号。

## 改动与影响范围

| 修改点 | 位置 | 内容 |
|:--:|:--:|:--:|
| `RemoteFreeHint` | `slab/mod.rs` | 一个 `AtomicU16`，每个 size class 一位，放在 slab 锁之外。`mark` 置位，`take` 清位并返回原值，`clear` 全清 |
| 远程释放登记 | `SlabTrait::dealloc_remote`、`PerCpuSlab::dealloc_remote` | 对象入队之后，按 `queue_remote_free` 返回的 size class 调 `mark` |
| `SlabTrait::remote_free_hint()` | `slab/mod.rs` | 默认返回 `None`，即每次都遍历，原有实现的行为不变 |
| `SlabAllocator::alloc_hinted` | `slab/mod.rs` | 带提示的分配入口；`alloc` 等价于提示为 `None` |
| `SlabCache::alloc_object_hinted` | `slab/cache.rs` | partial 取不到对象之后才询问提示，已登记才遍历 full 链表；`alloc_object` 等价于恒为已登记 |
| `reclaim_full_with_remote_frees` | `slab/cache.rs` | 一次遍历把所有带远程释放的 full slab 都移回 partial，此前只移第一个 |
| `SlabPageHeader::queue_remote_free` | `slab/page.rs` | crate 内部接口，返回对象所属的 size class；公开的 `remote_free_object` 签名不变 |
| `PercpuSlab` | `ax-alloc/src/buddy_slab.rs` | 持有一个 `RemoteFreeHint`，分配走 `alloc_hinted`，初始化时清空 |

次序上的两点保证不丢释放：释放方先入队、后置位；属主先清位、后遍历。遍历途中新到的释放会把位重新置上，下一次 partial 取空时再遍历。提示只在 partial 取不到对象之后才消费，partial 命中不会吃掉它。

影响范围：`ax-alloc` 的 `buddy-slab` 后端，即经它分配的全部内核小对象。公开接口没有变化。当前 dev 上这些代码原样保留：`RemoteFreeHint` 在 `slab/mod.rs`，`alloc_object_hinted` 与 `reclaim_full_with_remote_frees` 在 `slab/cache.rs`，`queue_remote_free` 在 `slab/page.rs`。

与 Linux 的差异：Linux 的 SLUB 没有这次遍历。对象释放回一个已满的 slab 时，释放方自己取节点的 `list_lock`，把这个 slab 挂回 partial 链表；full 链表只在开了 `SLAB_STORE_USER` 调试时才维护。这个分配器的远程释放路径不取锁，所以仍由属主在分配时去找。补丁之后，没有登记时不遍历；有登记时仍要线性走完该 size class 的整条 full 链表。

## 溯源复核

- 第一版（09.08）在进入 `alloc_object` 之前就消费提示。同一 size class 既有可用的 partial slab、又有收到远程释放的 full slab 时，分配从 partial 成功返回，提示却已清掉，那批远程释放的对象之后不再被找到。评审指出后改为 partial 取空才询问，对应用例 `a_partial_slab_hit_does_not_swallow_a_pending_remote_free`。
- 第二版（09.09）一次遍历仍只回收第一个带远程释放的 full slab，而提示已清。两个 full slab 都收到远程释放时，另一个留在 full 链表上。评审指出后改为一次遍历回收全部，对应用例 `one_walk_reclaims_every_full_slab_with_remote_frees`。
- 前两版还改了公开接口 `SlabCache::alloc_object` 与 `SlabPageHeader::remote_free_object` 的签名。合入的版本保留原签名，新语义放在 crate 内部的 `alloc_object_hinted` 与 `queue_remote_free` 里。
- 集成测试此前因缺少宿主机 `SpinOps` 后端一直链接不上，没有进过 `cargo xtask test`。接上之后暴露出四个用例的并行竞态：测试上下文先于分配器析构时，分配器在测试锁之外清掉全局单例标志。PR 里靠调整声明顺序解决。

## Linux 依据

- `__slab_free()`：释放前 `freelist` 为空即 slab 已满（[mm/slub.c#L5535](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/mm/slub.c#L5535)），此时取节点的 `list_lock`（[mm/slub.c#L5548-L5562](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/mm/slub.c#L5548-L5562)），释放成功后把 slab 加回 partial 链表（[mm/slub.c#L5594-L5597](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/mm/slub.c#L5594-L5597)）

## 验证

数字取自 PR 正文。

- `allocation_without_remote_frees_leaves_the_full_list_alone`：没有跨 CPU 释放时不遍历。修复前 512 次分配遍历 2701 个节点。
- `an_announced_remote_free_comes_back_to_the_owner`：登记过的释放经一次遍历取回。
- `a_partial_slab_hit_does_not_swallow_a_pending_remote_free`：partial 命中不消费提示。
- `one_walk_reclaims_every_full_slab_with_remote_frees`：两个 full slab 上的远程释放都能取回；在只回收第一个 full slab 的实现上失败，报 `a remote free on another full slab was stranded after the walk`。
- `cargo xtask test --since 1d7f3c20` 与 `cargo xtask clippy --since 1d7f3c20` 全部通过。
