## 问题与原因

PR 的目标是在适配浏览器之前，把浏览器依赖的一批系统调用行为逐项对到 Linux。内核侧实际改了三类代码：Unix 套接字与套接字系统调用、内存（`mprotect`、`madvise`、memfd 封印）、事件循环（epoll 边沿触发、`splice`）。补丁之前的行为如下。

Unix 套接字：

- `sys_socket` 没有 `(AF_UNIX, SOCK_SEQPACKET)` 分支。`sys_socketpair` 把 `SOCK_SEQPACKET` 与 `SOCK_DGRAM` 写在同一个分支里，建出的是一对数据报传输。`getsockopt(SO_TYPE)` 对所有 Unix 套接字固定返回 `SOCK_STREAM`。
- `DgramTransport::recv` 不看 `MSG_PEEK`，每次都把包从队列里取走；缓冲区比报文小时只打一条日志，不置 `MSG_TRUNC`。
- `recv_impl` 安装收到的 fd 时固定调用 `add_file_like(f, false)`，`MSG_CMSG_CLOEXEC` 不起作用。控制缓冲区装不下全部 fd 时，`push_sized` 返回假，整条 `SCM_RIGHTS` 不交付，`msg_flags` 里也没有 `MSG_CTRUNC`。流式套接字带 `MSG_PEEK` 接收时不交付控制消息。
- `sys_accept4` 不校验 `flags`。在没有连接队列的流式套接字上 `accept` 返回 `ENOTCONN`，在数据报套接字上返回 `EINVAL`。
- `sys_sendmmsg`、`sys_recvmmsg` 在 `vlen` 大于 1024 时返回 `EINVAL`。`recvmmsg` 不识别 `MSG_WAITFORONE`，`vlen` 大于队列里的报文数时会阻塞在下一次接收上。
- `UnixSocketAddr::write_to_user` 把 `AF_UNIX`（`linux_raw_sys` 里是 `u32`）整个写出，`sun_family` 占了 4 字节，`sun_path` 后移 2 字节，回写的 `addrlen` 也多 2。`getsockname`、`getpeername`、`accept`、`recvfrom` 回填的 Unix 地址都受影响。

内存：

- `sys_madvise` 把 `MADV_FREE` 与 `MADV_DONTNEED` 放在同一个分支，不看映射类型；`MADV_REMOVE` 落进 `_ => {}`，什么都不做就返回 0。
- `sys_mprotect` 对「只读打开的文件做 `MAP_SHARED` 映射，再升级到 `PROT_WRITE`」不报错。diff 里的注释说明原因：区域级的 `protect()` 只返回布尔值，权限不足的错误在下游被吞掉。
- memfd 的 `F_SEAL_ALL` 不含 `F_SEAL_FUTURE_WRITE`（`0x0010`），`add_seals` 对它返回 `EINVAL`。

事件循环：

- `EPOLLET` 的条目上报之后，`poll_events` 重新登记唤醒器，随即按 `IN | RDHUP | HUP` 复查文件的当前状态，仍然就绪就重新入队。于是没读完的 fd 在没有新事件时会被再次上报，行为等同水平触发。
- `do_send` 没有非阻塞参数，`splice` 带 `SPLICE_F_NONBLOCK` 且源是空管道时阻塞在读上。

PR 正文还列了线程的 TLS 与 tid 清理、`arch_prctl`、W^X 往返、非阻塞并发建连几项。这几项在 diff 里只有用例，没有内核改动，见「溯源复核」。

## 溯源复核

- 编号与分支名沿用自另一件事。#1569 创建于 2026-07-10，分支叫 `test-app-dnsmasq`，当天得到的批准与第一条行内评论（`apps/starry/dnsmasq/prebuild.sh`）针对的是 dnsmasq 用例；7 月 30 日起的评审写明旧意见属于早先的 head，当前 47 个文件已不含那条路径。本文所述内容是 7 月 30 日之后的版本。
- PR 正文的清单与 diff 的对应关系：「`clone` 的 `CLONE_SETTLS`、`CLONE_CHILD_CLEARTID`、`CLONE_PARENT_SETTID`」「`arch_prctl` 与 pkey」「W^X 往返」「非阻塞 `connect` 并发建连」四项只有用例（`syscall-test-clone-tls`、`syscall-test-archprctl-tls`、`syscall-test-mprotect-wx`、`syscall-test-nonblock-connect`），内核的线程退出、`arch_prctl`、`connect` 路径没有改动，这些行为在补丁之前就已具备。`mprotect` 方面的内核改动只有只读共享映射的 `EACCES`。反过来，diff 里有几项正文没有提：`sun_family` 的宽度、Unix 套接字的 `SO_TYPE`、数据报的 `MSG_PEEK` 与 `MSG_TRUNC`、`MSG_OOB` 的 `EOPNOTSUPP`、`SCM_RIGHTS` 的部分交付与 `MSG_CTRUNC`。
- 正文把 `MADV_FREE` 写作「惰性回收」。合入时的实现是校验通过后立即 `discard_range`，与 `MADV_DONTNEED` 同一个调用，没有延迟。这在手册允许的范围内（内核「可以」随时释放），但不是惰性的。当前 dev 已改为 `mark_lazy_free`。
- `MADV_REMOVE` 合入时有三点与 Linux 不同。其一，打洞是用 `write_at` 循环写零实现的，读回为零，但页没有释放。其二，`punch_shared_file_backend` 只认 memfd，后备不是 memfd 的共享文件映射返回 `Ok(false)`，调用方丢弃这个返回值，`madvise` 返回 0 而什么都没做；Linux 交给文件系统的 `fallocate`，不支持的返回 `EOPNOTSUPP`。其三，私有文件映射返回 `EINVAL`，Linux 对「不是可写共享映射」返回 `EACCES`，`EINVAL` 只用于没有文件或已锁定的映射。前两点在当前 dev 上已随重写消除；第三点还在：取不到共享文件映射的片段一律返回 `EINVAL`（`mmap.rs` 第 1425、1426 行）。
- `sys_fallocate` 对带写封印的 memfd 一律返回 `EPERM`，不看 `mode`。Linux 的 `shmem_fallocate` 只在 `FALLOC_FL_PUNCH_HOLE` 分支里检查 `F_SEAL_WRITE | F_SEAL_FUTURE_WRITE`，普通预分配只受 `F_SEAL_GROW` 约束。diff 里的注释说 `shmem_fallocate`「检查同一个掩码」，只对打洞成立。这个差异对 `F_SEAL_WRITE` 早已存在，补丁把它延伸到 `F_SEAL_FUTURE_WRITE`，当前 dev 未改。
- `F_SEAL_FUTURE_WRITE` 与 `mprotect`：`sys_mprotect` 对请求 `PROT_WRITE` 的共享 memfd 映射调用 `check_write_seal`，不区分映射建在封印之前还是之后，一律 `EPERM`。Linux 只在 `mmap` 时处理封印：封印之后新建的只读共享映射被清掉 `VM_MAYWRITE`，之后升级写权限得到 `EACCES`；封印之前建的映射保留 `VM_MAYWRITE`，可以照常 `mprotect`。两种情况的结果都与 StarryOS 不同（错误码不同，或本应成功）。
- `SOCK_SEQPACKET` 的监听状态合入时没有实现。`UnixSocket::listen` 当时对所有类型都是空操作，连接队列在 `bind` 时安装，所以对「已绑定但未 `listen`」的套接字，`connect` 会成功（Linux 返回 `ECONNREFUSED`），`accept` 会取连接或阻塞（Linux 返回 `EINVAL`）；补丁加的 `EINVAL` 实际只覆盖「未绑定」。流式套接字当时同样如此。当前 dev 已补上 `listen` 与 `listening` 标志。另一点至今未变：`try_send` 不区分 `is_seqpacket`，带目标地址时仍按数据报的路径去找 `slot.dgram`；Linux 的 `unix_seqpacket_sendmsg` 忽略地址，未连接时返回 `ENOTCONN`。
- `rights_capacity` 把剩余控制空间向下对齐到 8 字节再减去头部（沿用 `push_sized` 原有的算法）。64 位上控制缓冲区为 `CMSG_LEN(sizeof(int))` 即 20 字节时，算出的容量是 0，一个 fd 也不交付，只置 `MSG_CTRUNC`；Linux 的 `scm_max_fds` 不做对齐，同样的缓冲区能交付 1 个。当前 dev 的 `push_rights` 用 `body_capacity`，没有向下对齐，这一差异已消除。
- 253 的上限按单条控制消息检查。Linux 的 `scm_fp_copy` 按一次 `sendmsg` 累计（`fpl->count + num > fpl->max`），一条消息里带多条 `SCM_RIGHTS` 时两者不同。当前 dev 未改。
- `recvmmsg` 的 `vlen` 截到 1024 是 StarryOS 自己的限制，Linux 的 `do_recvmmsg` 不截；代码注释已如实说明，PR 正文把两者并称「`vlen` 钳制」。
- `EPOLLET` 的改动删掉的那段代码，原注释说明它是为了补一个丢事件的窗口：送达事件的那次唤醒已经消耗了唤醒器，在重新登记之前到达的新数据没有唤醒对象。补丁去掉复查之后，这个窗口重新打开。Linux 没有对应的窗口，epoll 的回调一直挂在文件的等待队列上，`ep_send_events` 只决定是否把条目放回就绪链表。按「读到 `EAGAIN`」的用法，窗口内到达的数据会被同一轮读走；只读一部分就返回等待的程序可能漏掉一次边沿。当前 dev 的 `EPOLLET` 分支仍不复查，登记机制后来改过，是否仍可触发待核实。
- `splice` 的非阻塞判断只看 `has_data()`，即源的 `poll()` 是否含 `IN`。按当前 dev 的管道实现，写端全部关闭的空管道只报 `HUP`，于是带 `SPLICE_F_NONBLOCK` 时返回 `EAGAIN`；Linux 的 `splice_from_pipe_next` 与 `ipipe_prep` 都先判断「没有写者」并返回 0，再看非阻塞标志。
- 新增与修改的 13 个用例里，6 个已不在当前 dev 上：`syscall-test-archprctl-tls`、`syscall-test-epoll-et`、`syscall-test-madvise`、`syscall-test-mmsg`、`syscall-test-seqpacket`、`syscall-test-splice-carpet` 被 #2404（2026-09-14 合入）删除。其余 7 个仍在。
