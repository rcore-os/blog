## 问题与原因

`CachedFile::set_len` 缩短文件时只做一件事：在 `old_last_page > new_last_page` 时把页号大于新末页的缓存页丢掉。新末页里新长度之后的字节不清零；如果缩短前后末页是同一页（`old_last_page == new_last_page`），这个分支不进，页缓存完全不动。缩短后页缓存里的新末页仍带着旧数据，之后凡是不经过 `set_len` 扩展分支而看到这段尾部的路径，都会读到旧数据。

PR 正文给的实例是 sqlite 的 WAL 模式：连接对 `-shm` 文件做 `ftruncate(fd, 3)` 以触发 wal-index 重建，随后 `mmap` 该文件。Linux 上映射读到零，头部无效，于是从 `-wal` 恢复；StarryOS 上读到残留的旧 wal-index 头，校验通过而不恢复，表现为另一个进程读不到表。以 sqlite 为元数据引擎的 juicefs 在 `format` 之后跨进程 `status` 失败。

## 改动与影响范围

| 修改点 | 内容 |
|:--:|:--:|
| 缩短分支的条件 | 由 `old_last_page > new_last_page` 改为 `len < old_len`，同一页内的缩短也进入 |
| 末页尾部清零 | `tail = len % PAGE_SIZE` 不为 0 且新末页在页缓存里时，`page.data()[tail..].fill(0)`，并置 `page.dirty = true` |
| 丢弃多余的页 | 逻辑不变，放在清零之后 |
| 扩展分支 | 原有的 `fill(0)` 之后补 `page.dirty = true` |

两处 `dirty` 是评审指出后补的：补丁注释说明底层 ext4 的 `set_len` 只改 `i_size`、不清磁盘上的字节，不标脏的话这一页被当作干净页淘汰后重新读入，旧数据会回来。

影响范围：经 `CachedFile` 的 `truncate`、`ftruncate`，包括磁盘文件与 tmpfs 文件；以及这些文件上的 `mmap` 与读。

与 Linux 的差异：清零只在新末页已在页缓存里时发生。末页不在缓存时什么都不做，磁盘上新长度之后的旧字节留着；Linux 的 ext4 在截断时会把 `i_size` 所在块的尾部在磁盘上清零。

当前 dev：`set_len` 移到 `fs/ax-fs-ng/src/file/cache/resize.rs` 第 588 行并重写。缩短时仍清零新末页的尾部，改由 `prepare_zero_write_locked` 完成：它用 `with_page_or_insert` 取页，不再以页已在缓存里为前提，清零后先落盘再调用底层 `set_len`。合入时的这段代码已不存在。

## 溯源复核

- 回归用例在修复前也会通过，没有起到验证修复的作用。用例的步骤是写满一页 `0xAA`，`ftruncate` 到 100，再 `ftruncate` 回 4096，`pread` 检查 `[100, 4096)` 为零。合入前的 `set_len` 在扩展分支（`old_len < len`）里已经有 `page.data()[old_page_offset..new_page_offset].fill(0)`：第二次 `ftruncate` 从 100 扩到 4096 时，旧代码就会把缓存页的 `[100, 4096)` 清零，`pread` 读到的是零。用例注释写「旧 starry……导致 regrow 后读到残留的 0xAA」，与合入前的代码不符。要复现缺陷，需要缩短之后不经 `ftruncate` 扩展而直接看到页尾，例如 PR 正文说的 `mmap`。这是按代码推断的结论，未在旧提交上实跑；PR 里也没有用例在修复前失败的记录。
- 机器人评审把这条用例描述为「直接回归验证本 PR 修复的 sqlite WAL 场景」，同样不成立，原因同上。
- 补丁只处理末页在缓存里的情形，见上面「与 Linux 的差异」。当前 dev 已不依赖这一前提。

## man 原文

[truncate(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/truncate.2?h=man-pages-6.19#n53)：

> If the file previously was larger than this size, the extra data is lost. If the file previously was shorter, it is extended, and the extended part reads as null bytes ('\0').

[mmap(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/mmap.2?h=man-pages-6.19#n770)：

> For a file that is not a multiple of the page size, the remaining bytes in the partial page at the end of the mapping are zeroed when mapped, and modifications to that region are not written out to the file.
