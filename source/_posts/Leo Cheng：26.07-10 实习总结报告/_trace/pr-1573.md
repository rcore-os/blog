## 问题与原因

hwloc、pocl、numactl 与 libnuma 从 sysfs 读 CPU 的缓存层级、CPU 拓扑与 NUMA 节点内存。StarryOS 的 `/sys/devices/system/cpu/cpuN` 下没有 `cache/` 与 `topology/`，也没有 `/sys/devices/system/node/`，这些程序拿不到数据。

## 改动与影响范围

| 修改点 | 位置 | 内容 |
|:--:|:--:|:--:|
| 缓存层级 | `sysfs/cache.rs` | 每个逻辑 CPU 在自己上面读架构寄存器：x86_64 读 `CPUID` 叶 4，没有叶 4 时退到叶 2；aarch64 读 `CLIDR_EL1` 与 `CCSIDR_EL1`；loongarch64 读 `CPUCFG`。riscv64 没有这类寄存器，Linux 走设备树，这里不暴露 `cache/` |
| 采样方式 | `init_cpu_cache()` | 挂载 `/sys` 之前，主核直接读，其余在线核经 `run_on_cpu_sync` 在本核读。回调跑在硬中断上下文，只把结果写进调用方栈上的定长缓冲，不分配、不取锁；返回后在任务上下文里发布。调用失败的 CPU 不暴露 `cache/` |
| `cache/indexN` 的属性 | `CpuCacheIndexDir` | `level`、`type`、`size`、`coherency_line_size`、`ways_of_associativity`、`number_of_sets`、`physical_line_partition`、`shared_cpu_map`、`shared_cpu_list`。硬件没有报告的几何属性不出现 |
| 共享范围 | `leaf_scope()`、`shared_cpus()` | 没有共享线程数时：L1 私有，其余由全部有缓存信息的 CPU 共享。x86 有共享线程数时：等于 1 为私有；其余由 APIC id 去掉低 `get_count_order(num_threads_sharing)` 位之后相等的 CPU 共享。每个 CPU 采样时一并记下自己的 APIC id |
| 拓扑 | `sysfs.rs` | `core_id`、`physical_package_id`、`core_cpus`、`thread_siblings`、`core_siblings`、`package_cpus` 及各自的 `_list`；`cluster_*` 只在 x86_64、aarch64、riscv64 出现，`die_*` 只在 x86_64 出现 |
| CPU 位图与列表 | `format_cpu_mask()`、`format_cpu_list()` | 位图按 32 位一组输出，超过 64 个 CPU 不截断；所有 cpulist 文件走同一个列表格式化函数 |
| NUMA 节点 | `sysfs.rs` | `node/node0` 下的 `meminfo`、`distance`、`cpumap`、`cpulist` 等；`meminfo` 与 `/proc/meminfo` 共用同一份分配器统计 |
| `/proc/meminfo` | `pseudofs/proc.rs` | 求和改用公共的 `allocator_used_bytes` |

影响范围：只新增 sysfs 节点，另把 `/proc/meminfo`、`/proc/vmstat` 与节点 `meminfo` 的内存统计并到一处。PR 未合入，当前 dev 上没有这些代码。

与 Linux 的差异：

| 项 | Linux | 本 PR |
|:--:|:--:|:--:|
| 拓扑 | 由 APIC id 或固件给出核、线程、封装的关系 | 一个封装、每核一个线程；SMT 的兄弟线程不体现 |
| AMD 与 Hygon 的缓存 | 读叶 0x8000001D | 没有读，`cache/` 不出现 |
| NUMA | 多节点 | 只有 `node0` |
| riscv64 的缓存 | 读设备树 | 不暴露 |

```rust
fn leaf_scope(level: u32, threads_sharing: Option<u32>) -> SharingScope {
    match (level, threads_sharing) {
        (1, None) | (_, Some(1)) => SharingScope::Private,
        (_, None) => SharingScope::SystemWide,
        (_, Some(n)) => SharingScope::ApicDomain {
            order: n.next_power_of_two().trailing_zeros(),
        },
    }
}
// ...
let owner = apic_ids.get(cpu).copied().flatten();
apic_ids.iter().enumerate().filter_map(move |(i, &apic)| {
    let joins = i == cpu
        || match (scope, owner.zip(apic)) {
            (_, None) | (SharingScope::Private, _) => false,
            (SharingScope::SystemWide, _) => true,
            (SharingScope::ApicDomain { order }, Some((a, b))) => a >> order == b >> order,
        };
    joins.then_some(i)
})
```

## 溯源复核

- PR 从 07.11 到 09.28 经历了二十九轮评审。反复出现的问题有三类：缓存的共享范围（先报成全系统共享，再改成只报本 CPU，再改成按共享线程数区分，最后才是按 APIC id 分组）；跨 CPU 采样回调里分配内存，违反硬中断上下文的约定；文档与注释落后于实现。
- 09.28 的三条意见都成立，10.04 推送的版本一并处理。其中分量最重的一条：x86 上「共享线程数介于 1 与在线 CPU 数之间」时两个 `shared_cpu_*` 属性整个缺失，而这正是 SMT 与多末级缓存机器的常见情形。
- 09.28 的版本在真实的 SMT 拓扑上确实出错。QEMU 以 1 路 2 核 2 线程启动时，L1 与 L2 共 12 个叶都没有共享集合；Linux 给的是 `0-1` 与 `2-3`。套件用的 `-smp 4` 是平面拓扑，L1、L2 的共享线程数是 1，L3 等于在线 CPU 数，所以二十九轮评审里没有一次跑到这个分支。
- 做这组对照时发现 xtask 会把 `-smp` 的拓扑参数规整成 CPU 个数，前一次「SMT 拓扑下的红绿」其实跑在平面拓扑上，结果无效。拓扑改经 `-machine q35,smp.sockets=…` 给出后才生效。
- 系统用例原来断言「每个 L1 都是私有的」，这在 SMT 机器上不成立。10.04 改为在用户态读 `CPUID.4` 与每个 CPU 的 APIC id，按 Linux 的规则算出期望集合再逐叶比较，对任何 x86 拓扑都成立。
- 仍未解决的两处写进了应用的 README：`topology/` 不体现 SMT，本版本的 L1 `shared_cpu_list` 会列出两个兄弟线程，而 `thread_siblings` 仍只有自己；AMD 与 Hygon 的处理器不用叶 4 报告缓存，在它们上面 `cache/` 不出现。
