## 问题与原因

已连接的 `AF_UNIX` 流式套接字，两端的 `Channel` 共用同一个 `PollSet`：`new_channels` 只建一个 `poll_update`，客户端与服务端各持一份克隆。`register_poll_sources` 把等待者挂在 `chan.poll_update` 上，`try_send`、`try_recv`、`shutdown`、`Drop` 也都唤醒它。于是发起操作的一端自己的等待者同样被叫醒：`try_send` 以 `IN | OUT` 唤醒，发送端自己等 `OUT` 的等待者、对端等 `OUT` 的等待者都被触发；`try_recv` 以 `OUT` 唤醒，接收端自己等 `OUT` 的等待者被触发。

`StreamTransport::poll()` 只要发送缓冲有空位就报告 `OUT`，这个条件在多数时候为真。边沿触发的 epoll 每被唤醒一次就重新取一次状态并上报一次 `EPOLLOUT`，所以一端每做一次读或写，就在自己身上产生一个状态并未变化的可写事件。tokio、libuv 这类边沿触发的事件循环因此不停被叫醒；本地记录里的复现是单核 loongarch64 上 `uv pip` 占满 CPU。

Linux 的等待队列属于各自的 `struct sock`：发送只通知对端可读，发送端的可写通知由对端消费数据、释放缓冲时触发。

## 改动与影响范围

| 修改点 | 内容 |
|:--:|:--:|
| `new_channels` | 建两个 `PollSet`（`client_poll`、`server_poll`）；每端的 `poll_update` 是自己的，新字段 `peer_poll_update` 指向对端的 |
| `Channel` | 新增字段 `peer_poll_update: Arc<PollSet>` |
| `try_send` | 唤醒对象由 `poll_update` 改为 `peer_poll_update`，事件由 `IN \| OUT` 改为 `IN` |
| `try_recv` | 唤醒对象改为 `peer_poll_update`，事件仍是 `OUT`；带 `MSG_PEEK` 时不唤醒（未改） |
| `shutdown` | 写半关闭、两半都关闭后回收通道这两处，唤醒对象改为 `peer_poll_update`，事件仍是 `IN \| OUT \| RDHUP`；本端的 `poll_state` 唤醒未改 |
| `Drop` | 唤醒对象改为 `peer_poll_update`，事件仍是 `IN \| RDHUP`；本端的 `poll_state` 唤醒未改 |

等待者的注册没有改：`register_poll_sources` 仍把等待者挂到本端的 `chan.poll_update` 与 `self.poll_state`。两端各有一个集合之后，这就成了「只在自己这端等」。

影响范围：`socketpair(AF_UNIX, SOCK_STREAM)` 与 `connect`/`accept` 建立的流式连接上，`read`/`write`/`send*`/`recv*`/`shutdown`/`close` 引起的唤醒，以及在这些套接字上等待的 `poll`、`select`、`epoll`。环形缓冲、控制消息队列、关闭标志的同步关系没有动。

当前 dev：代码仍在 `net/ax-net/src/unix/stream.rs`。两个集合的接线在第 91、92、105、106 行，字段在第 133 行；`try_send` 的唤醒在第 440、447 行，`try_recv` 在第 493、506 行，`shutdown` 在第 570 至 581 行，`Drop` 在第 668 至 674 行。

## 溯源复核

- QEMU 用例 `bugfix-unix-stream-peer-wake` 已不在当前 dev 上：#2404（2026-09-14 合入，把一批 bugfix 与 syscall 探针迁往 LTP）删除了它的两个文件，距本 PR 合入两天。三个单测还在，位于 `stream.rs` 第 729、750、769 行。
- 可写通知的门槛与 Linux 不同。Linux 的接收路径只在一个 skb 被整个读完后才释放它，释放时经 `sock_wfree` 调发送端的 `unix_write_space`，后者仅当 `unix_writable` 成立（已占用的发送内存不超过 `sk_sndbuf` 的四分之一）才唤醒。`try_recv` 只要读走了字节就以 `OUT` 唤醒对端，`poll()` 只要缓冲有空位就报可写。写满后被对端逐小块读取时，StarryOS 的写端比 Linux 更早、更频繁地得到可写边沿。这是补丁之前就有的行为，补丁只改了唤醒对象。
- 对端关闭时的唤醒比 Linux 窄。Linux 的 `unix_release_sock` 把对端的 `sk_shutdown` 置为 `SHUTDOWN_MASK` 后调 `sk_state_change`，即 `sock_def_wakeup`，不带事件过滤地唤醒对端全部等待者，随后 `unix_poll` 报告 `EPOLLHUP`。`Drop` 以 `IN | RDHUP` 唤醒对端，`PollSet` 按 `interests.intersects(ready)` 过滤，只关心 `OUT` 的等待者不会被这次唤醒叫到；`StreamTransport::poll()` 也只产生 `IN`、`OUT`、`RDHUP`，不产生 `HUP`。事件掩码不是本补丁改的。
- 只关闭读半（`SHUT_RD`）时不通知对端：`shutdown` 里 `peer_poll` 只在 `how.has_write()` 或两半都已关闭时赋值。Linux 的 `unix_shutdown` 在 `RCV_SHUTDOWN` 时给对端置 `SEND_SHUTDOWN` 并调对端的 `sk_state_change`。同样是补丁之前就有的行为。

## man 原文

[epoll(7)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man7/epoll.7?h=man-pages-6.19#n122)：

> The reason for this is that edge-triggered mode delivers events only when changes occur on the monitored file descriptor, that is, an event will be generated upon each receipt of a chunk of data.

[epoll_ctl(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/epoll_ctl.2?h=man-pages-6.19#n97)：

> EPOLLRDHUP (since Linux 2.6.17) Stream socket peer closed connection, or shut down writing half of connection. (This flag is especially useful for writing simple code to detect peer shutdown when using edge-triggered monitoring.)

手册没有规定「哪一端的操作唤醒哪一端」，每端一个等待队列是 Linux 实现的结构，依据在源码里。

- 单测 `send_wakes_only_the_peer_reader`：`try_send` 四个字节后，对端等 `IN` 的观察者被唤醒一次，发送端等 `OUT`、对端等 `OUT` 的观察者都是零次。
- 单测 `recv_wakes_only_the_peer_writer`：`try_recv` 读走数据后，发送端等 `OUT` 的观察者被唤醒一次，接收端自己等 `OUT` 的观察者零次。
- 单测 `write_shutdown_and_drop_wake_the_peer`：`shutdown(Write)` 与 `drop` 各自唤醒对端等 `IN | RDHUP` 的观察者一次。
