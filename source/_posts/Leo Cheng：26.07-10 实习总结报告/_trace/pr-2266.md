## 问题与原因

两处权限检查缺失，叠在一起可以从非特权进程拿到全部能力位：

- `setns(2)` 的 nsfd 与 pidfd 两条路径只在目标是 cgroup 命名空间时检查 `CAP_SYS_ADMIN`。非特权进程可以加入别的进程的 UTS、IPC、NET、MNT、PID、USER 命名空间。
- `/proc/<pid>/uid_map` 与 `gid_map` 的写入不校验写入者。非特权进程 `unshare` 出一个 user namespace 后写 `0 0 1`，就把自己映射成宿主的 uid 0。

只补第一处不够：StarryOS 的能力位不按 user namespace 区分，进程在子 user namespace 里拿到的 `CAP_SYS_ADMIN` 会被当成全局的。所以第二处不堵，第一处的检查可以经「先映射成 root 再 setns」绕过。

## 改动与影响范围

| 修改点 | 位置 | 内容 |
|:--:|:--:|:--:|
| `in_initial_user_ns()` | `namespace/mod.rs` | 判断进程的 user namespace 是否仍是初始的那个 |
| `may_join()` | `syscall/task/namespace.rs` | `setns` 两条路径对所有命名空间类型要求：持有 `CAP_SYS_ADMIN`，并且调用者位于初始 user namespace；否则 `EPERM` |
| `may_map_id()` | `pseudofs/proc.rs` | 写 `uid_map`/`gid_map` 时，要么只映射一个 id 且它是写入者自己的 euid/egid，要么写入者位于初始 user namespace 并持有 `CAP_SETUID`/`CAP_SETGID`；否则 `EPERM` |

影响范围：`setns` 的全部命名空间类型，以及 `uid_map`、`gid_map` 的写入。这三处在当前 dev 上原样保留，用例也在。

与 Linux 的差异。补丁是有意做得比 Linux 更严、更简单的过渡方案，因为 StarryOS 还没有 user namespace 的父子链，也没有记录每个命名空间属于哪个 user namespace：

| 项 | Linux | 本补丁 |
|:--:|:--:|:--:|
| 加入 UTS、IPC 等命名空间 | 调用者在自己的 user namespace 与目标命名空间所属的 user namespace 里都持有 `CAP_SYS_ADMIN` | 调用者必须在初始 user namespace 里持有 `CAP_SYS_ADMIN` |
| 子 user namespace 里的进程 | 可以加入同属这个 user namespace 的其他命名空间 | 一律不能 `setns` |
| 无特权写 id 映射 | 只能写一行、映射自己的 euid/egid，且写入者的 euid 等于创建该命名空间的进程的 euid；写 `gid_map` 还要求 `setgroups` 已设为 `deny` | 只检查「一个 id、是自己的」，不比对命名空间的创建者，不要求 `setgroups` 为 `deny` |
| 有特权写 id 映射 | 在父 user namespace 里持有 `CAP_SETUID`/`CAP_SETGID`，且打开文件的进程也持有 | 在初始 user namespace 里持有 |

PR 正文写明了前两条代价与 `setgroups` 这一条；后者是因为现有用例 `claw-code-regression/goal-03-gid-map` 依赖不设 `deny` 就能写 `gid_map`。

## 溯源复核

- 「无特权写入者的 euid 须等于命名空间创建者的 euid」这一条 Linux 有而补丁没有，PR 正文没有提。后果是：进程 A 创建的 user namespace，另一个非特权进程 B 只要能打开 A 的 `uid_map` 就能把自己的 id 映射进去。打开 `/proc/<A>/uid_map` 本身的权限检查是否足以挡住这一点，没有核对，待核实。
- Linux 在映射里含 uid 0 时另有一道 `verify_root_map()`，补丁没有对应物。
- 评审第一轮（09.02）指出只加全局 `CAP_SYS_ADMIN` 检查达不到 user namespace 语义，现在的 `may_map_id()` 与「初始 user namespace」条件是这一轮之后加的；09.11 批准。

## Linux 依据

- 各类命名空间的 `install` 回调要求两处都持有 `CAP_SYS_ADMIN`，以 UTS 为例：[kernel/utsname.c#L127-L134](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/kernel/utsname.c#L127-L134)；IPC 同样：[ipc/namespace.c#L237-L239](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/ipc/namespace.c#L237-L239)
- 加入 user namespace：要求在目标 user namespace 里持有 `CAP_SYS_ADMIN`，且不能重入自己所在的那个：[kernel/user_namespace.c#L1343-L1362](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/kernel/user_namespace.c#L1343-L1362)
- `setns` 经 `ns->ops->install()` 进入上述回调：[kernel/nsproxy.c#L388](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/kernel/nsproxy.c#L388)
- `new_idmap_permitted()`：无特权时只允许单条、长度为 1、映射自身 id，且命名空间的属主等于写入者的 euid；否则要求在父 user namespace 里持有相应能力：[kernel/user_namespace.c#L1172-L1212](https://github.com/torvalds/linux/blob/8cd9520d35a6c38db6567e97dd93b1f11f185dc6/kernel/user_namespace.c#L1172-L1212)

## man 原文

[setns(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/setns.2?h=man-pages-6.19#n251)：

> Network, IPC, and UTS namespaces In order to reassociate itself with a new network, IPC, time, or UTS namespace, the caller must have the CAP_SYS_ADMIN capability both in its own user namespace and in the user namespace that owns the target namespace.

[user_namespaces(7)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man7/user_namespaces.7?h=man-pages-6.19#n705)：

> The data written to uid_map (gid_map) must consist of a single line that maps the writing process's effective user ID (group ID) in the parent user namespace to a user ID (group ID) in the user namespace.

> The writing process must have the same effective user ID as the process that created the user namespace.

## 验证

数字取自 PR 正文。

- `bugfix-setns-requires-cap-sys-admin` 以 root 启动，先打开初始 UTS、IPC、NET 的 nsfd 与自身的 pidfd，再在子进程里构造五种身份：初始 user namespace 的 root（加入成功）；降权到 65534（六次 `setns` 都 `EPERM`）；降权后写 `0 0 1`（映射 `EPERM`，uid 仍非 0）；降权后映射自身（映射成功，`setns` 仍 `EPERM`）；root 进入子 user namespace 并映射 `0 0 1`（映射成功，`setns` 仍 `EPERM`）。
- x86_64，基线 `1d7f3c20`：只加用例时 8 过 4 挂，后四种身份的 `setns` 全部成功，写 `0 0 1` 之后 uid 变成 0；加上修复后 12 项全过。
- Linux 6.6 上以 root 实跑全过。
