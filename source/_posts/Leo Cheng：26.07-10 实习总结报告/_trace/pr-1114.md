## 问题与原因

合入的 diff 含五项互相独立的修复。PR 标题与正文还列了第六项（axfs-ng 文件缓存尾页清零）和 `riscv_hwprobe` 桩，二者都不在合入的 diff 里，见「溯源复核」。

1. `/proc/sys/kernel` 下没有 `osrelease` 与 `ostype`。补丁注释举的例子是 juicefs 的 sqlite 元数据后端依赖的 `modernc.org/fileutil`，打开 `osrelease` 失败时直接 panic。
2. `MemoryFs::stat` 返回 `dummy_stat_fs(0x01021994)`，即 100 个 512 字节的块，总容量约 50 KiB。按可用空间做准入的服务端程序（补丁注释举 BookKeeper 的 `minUsableSizeForEntryLogCreation`，默认 1 GiB）在 tmpfs 上拒绝写入。
3. x86_64 与 aarch64 的 `USER_STACK_TOP` 是 `0x7fff_0000_0000`，用户空间上界是 `0x8000_0000_0000`，栈顶之上只剩 4 GiB；`sys_mmap` 的非 `MAP_FIXED` 选址以整个地址空间为范围，会用到这一段。按补丁注释，V8 的 4 GiB 指针压缩区预留因此只有一个提示地址可用、没有回退，`npm`、`vue`、`astro` 以 139 退出（#242）。这一因果只有补丁注释为据，PR 没有附复现记录。
4. `sys_madvise` 对所有建议值只检查起始地址是否落在某个映射内，然后返回 0。`MADV_DONTNEED` 与 `MADV_FREE` 不释放任何页帧。补丁注释指出 Go 运行时靠这两个建议归还空闲堆，长时间运行的进程占用因此只增不减。
5. `sys_fcntl` 不认识 `F_GET_RW_HINT`（1035）、`F_SET_RW_HINT`（1036）、`F_GET_FILE_RW_HINT`（1037）、`F_SET_FILE_RW_HINT`（1038）以及 `F_SETSIG`（10）、`F_GETSIG`（11）、`F_SETOWN_EX`（15）、`F_GETOWN_EX`（16），一律走默认分支返回 `EINVAL`。

## 改动与影响范围

| 修改点 | 位置 | 内容 |
|:--:|:--:|:--:|
| `osrelease`、`ostype` | `pseudofs/proc.rs` | `/proc/sys/kernel` 目录加两个只读文件，内容固定为 `6.6.0-starry\n` 与 `Linux\n` |
| `MemoryFs::stat` | `pseudofs/tmp.rs` | 不再调用 `dummy_stat_fs`，改报块大小 4096、总块数与空闲块数均为 `1 << 20`（4 GiB）、空闲 inode `1 << 16` |
| `USER_STACK_TOP` | `config/x86_64.rs`、`config/aarch64.rs` | 由 `0x7fff_0000_0000` 改为 `0x0400_0000_0000`（4 TiB），栈上方留出约 124 TiB |
| `STACK_GUARD_GAP` | `syscall/mm/mmap.rs` 的 `sys_mmap` | 非 `MAP_FIXED` 选址的两次 `find_free_area` 上界由 `aspace.end()` 收到 `USER_STACK_TOP - 1 MiB` |
| `AddrSpace::discard_range()` | `mm/aspace/mod.rs` | 新增。对区间内每个匿名私有映射（`Backend::Cow` 且 `is_anonymous()`）取交集、向内按后端页大小对齐，调用后端的 `unmap` 清页表项并释放页帧，映射本身保留，下次访问缺页得到零页。其余后端跳过 |
| `sys_madvise` | `syscall/mm/mmap.rs` | 长度为 0 直接返回；用 `can_access_range`（空权限掩码）检查整个区间连续映射，否则 `ENOMEM`；`MADV_DONTNEED`、`MADV_FREE`、`MADV_DONTNEED_LOCKED` 调用 `discard_range`，其余建议值仍只做校验 |
| 读写提示 | `syscall/fs/fd_ops.rs` 的 `sys_fcntl` | 1035 与 1037 向用户指针写回 `0u64`；1036 与 1038 从用户指针读 `u64`，大于 5 返回 `EINVAL`；都不保存状态 |
| 属主与信号命令 | 同上 | 10、11、15、16 直接返回 0 |

影响范围：读 `/proc/sys/kernel/{osrelease,ostype}` 的程序；对 tmpfs 调用 `statfs`/`fstatfs` 的程序；x86_64 与 aarch64 上所有进程的栈位置和非 `MAP_FIXED` 映射的选址范围（riscv64、loongarch64 的 `USER_STACK_TOP` 当时是 `0x4_0000_0000`，未改）；`madvise` 的返回值与三种丢弃类建议的效果；`fcntl` 的上述八个命令。

与 Linux 的差异：

- `osrelease` 是固定字符串，与 `uname(2)` 返回的 `release`（`10.0.0`）不是同一个来源，见「溯源复核」。
- tmpfs 容量是固定的 4 GiB，已用空间不计；Linux 默认是物理内存的一半，并按已用块数扣减空闲值。
- Linux 把栈放在用户地址空间顶端，映射区的基址在栈的下方；这里把栈降到 4 TiB，栈的上方留给映射。`STACK_GUARD_GAP` 的上界落在栈区内部（栈占 `[USER_STACK_TOP - 8 MiB, USER_STACK_TOP)`），效果是非 `MAP_FIXED` 的映射不会落到栈顶之上，栈底以下没有留出间隙。
- `MADV_FREE` 立即丢弃，等同 `MADV_DONTNEED`；Linux 是延迟回收，丢弃前写入会取消回收。
- `MADV_DONTNEED` 与 `MADV_FREE` 对文件映射、共享映射不做任何事并返回 0，见「溯源复核」。
- `F_SET_RW_HINT` 不检查调用者是否为文件属主，Linux 先做属主检查。

当前 dev：

- `osrelease`、`ostype` 仍在 `pseudofs/proc.rs`（第 2070、2074 行），内容未变。
- `MemoryFs` 移到 `fs/ax-fs-ng/src/fs/memory.rs`，`stat()` 在第 207 行，默认容量仍是 4 GiB（`DEFAULT_TMPFS_SIZE`），但已按挂载选项的大小上限与 `used_bytes` 计算总块数和空闲块数。
- 常量改名为 `USER_STACK_TOP_MAX`（`config/x86_64.rs` 第 18 行、`config/aarch64.rs` 第 13 行，值不变；loongarch64 现在也是 `0x0400_0000_0000`），实际栈顶由 `mm/layout.rs` 第 52 行按平台地址空间取小。`STACK_GUARD_GAP` 仍在 `syscall/mm/mmap.rs` 第 370 行，上界改用 `aspace.stack_top()`。
- `sys_madvise`（`syscall/mm/mmap.rs` 第 1375 行）已重写为按映射片段逐段处理，空洞只记录、最后返回 `ENOMEM`；`MADV_FREE` 改为 `mark_lazy_free` 的延迟回收并对非匿名私有映射返回 `EINVAL`；`discard_range`（`mm/aspace/mod.rs` 第 4226 行）已重写，不再只处理匿名私有映射。
- `sys_fcntl` 的这两段原样保留（`syscall/fs/fd_ops.rs` 第 979 至 998 行）。

## 溯源复核

- PR 标题与正文第 4 条的 axfs-ng 尾页清零不在合入的 diff 里：diff 没有 `axfs-ng` 下的文件。作者 2026-06-10 的评论说明这处改动与 #1164 对同一个 `page_or_insert` 的修改重复，已从本 PR 移除，归到 [#1164](pr-1164.md)。合入提交的标题是 `fix(starry): Linux-compat foundational fixes (pseudofs/mm/syscall) + regression tests`，PR 标题没有同步。
- PR 正文第 6 条的 `riscv_hwprobe` 桩同样不在合入的 diff 里。首轮评审指出新增的实现与 `syscall/sys.rs` 里已有的 `sys_riscv_hwprobe` 重名，riscv64 编译失败（`E0659`）；合入时 `syscall/` 下只有 `sys.rs` 里原有的那一份（合入提交的第 836 行）。
- `madvise` 遇到空洞的处理与 Linux 不同。补丁先用 `can_access_range` 检查整个区间，有空洞就返回 `ENOMEM`，不丢弃任何页。Linux 的 `madvise_walk_vmas` 遇到空洞只记下 `-ENOMEM`，继续对区间内其余映射执行，最后才返回该错误。返回值一致，副作用不一致：对 `[已映射][空洞][已映射]` 调用 `MADV_DONTNEED`，Linux 会清掉两段已映射的页，补丁一页不动。回归用例只断言返回 `ENOMEM`，没有检查两侧页的内容。当前 dev 已改成逐片段处理，这一改动首次出现在 #1775 的合入提交 `5a5e669354`（2026-09-08）的 `mmap.rs` 里。
- `discard_range` 跳过非匿名后端并返回成功。Linux 的 `MADV_DONTNEED` 不区分映射类型，对文件私有映射也会清掉页表项（写时复制产生的私有页随之丢弃，再次访问从文件重新读入）；`MADV_FREE` 作用于非匿名映射时返回 `EINVAL`。补丁在这两种情况下都返回 0 且不做任何事。当前 dev 的 `MADV_FREE` 对非匿名私有映射返回 `EINVAL`，`discard_range` 不再按后端类型跳过，只拒绝设备与线性映射。
- `1037`、`1038` 被当作 `1035`、`1036` 的同义命令。对照版本的 `do_fcntl` 只有 `F_GET_RW_HINT` 与 `F_SET_RW_HINT` 两个分支，`F_GET_FILE_RW_HINT`、`F_SET_FILE_RW_HINT` 只在 UAPI 头文件里保留了编号，进入 `do_fcntl` 后落到默认分支返回 `EINVAL`。补丁对这两个命令返回成功，与对照版本不一致；man-pages 6.19 仍列着这两个命令。当前 dev 未改。
- `10 | 11 | 15 | 16 => Ok(0)` 把四个有状态的命令做成了空操作。Linux 里 `F_SETSIG` 会校验信号编号（非法返回 `EINVAL`）并保存，`F_GETSIG` 返回保存的值，`F_GETOWN_EX` 向用户指针写回 `struct f_owner_ex`（坏指针返回 `EFAULT`），`F_SETOWN_EX` 从用户指针读入并校验类型与进程是否存在。补丁下 `F_GETSIG` 返回 0 与「从未设置」的 Linux 结果相同，其余三个不成立：`F_SETSIG` 的值被丢弃，`F_GETOWN_EX` 不写用户缓冲区，调用者读到的是未初始化内容，`F_SETOWN_EX` 不生效。这与评审对 `F_GET_RW_HINT` 提的问题（必须写回用户指针）是同一类，回归用例没有覆盖这四个命令。当前 dev 未改。
- `osrelease` 与 `uname(2)` 不一致。Linux 的 `/proc/sys/kernel/osrelease` 与 `uname` 读的是同一个 UTS 命名空间里的 `release` 字段。合入时 StarryOS 的 `uname` 返回 `10.0.0`（`os/StarryOS/axnsproxy/src/uts.rs` 第 56 行），当前 dev 仍是 `10.0.0`（`kernel/src/namespace/uts.rs` 第 67 行），而 `osrelease` 是 `6.6.0-starry`。同时读两处的程序会看到两个版本号。
- 回归用例已不在当前 dev 的树里，见「验证」。
- 补丁注释把 `STACK_GUARD_GAP` 类比为 Linux `mm/mmap.c::vma_compute_gap` 里的 `stack_guard_gap`。对照版本的 `mm/*.c` 与 `include/linux/*.h` 里没有 `vma_compute_gap` 这个函数；`stack_guard_gap` 现在经 `vm_start_gap()` 生效，保护的是向下增长的栈的下方，与补丁限制「不落到栈顶之上」不是同一件事。

## man 原文

[proc_sys_kernel(5)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man5/proc_sys_kernel.5?h=man-pages-6.19#n268)：

> /proc/sys/kernel/ostype /proc/sys/kernel/osrelease These files give substrings of /proc/version.

[tmpfs(5)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man5/tmpfs.5?h=man-pages-6.19#n69)：

> The default, when neither size nor nr_blocks is specified, is size=50%.

[madvise(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/madvise.2?h=man-pages-6.19#n103)：

> MADV_DONTNEED Do not expect access in the near future. (For the time being, the application is finished with the given range, so the kernel can free resources associated with it.)
>
> After a successful MADV_DONTNEED operation, the semantics of memory access in the specified region are changed: subsequent accesses of pages in the range will succeed, but will result in either repopulating the memory contents from the up-to-date contents of the underlying mapped file (for shared file mappings, shared anonymous mappings, and shmem-based techniques such as System V shared memory segments) or zero-fill-on-demand pages for anonymous private mappings.

[madvise(2)](https://git.kernel.org/pub/scm/docs/man-pages/man-pages.git/tree/man/man2/madvise.2?h=man-pages-6.19#n496)：

> MADV_FREE (since Linux 4.5) The application no longer requires the pages in the range specified by addr and size. The kernel can thus free these pages, but the freeing could be delayed until memory pressure occurs.
